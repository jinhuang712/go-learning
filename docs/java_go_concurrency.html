Java / Go 并发库对照

本文目标 对比 Java 的 java.util.concurrent 包和 Go 的 sync / channel 在并发编程中的差异。重点是心智模型:Java 是「共享内存 + 锁」, Go 是「不要通过共享内存来通信,而要通过通信来共享内存」。

2. 互斥锁

Java: ReentrantLock

import java.util.concurrent.locks.ReentrantLock;

ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}

Go: sync.Mutex

import "sync"

var mu sync.Mutex

mu.Lock()
defer mu.Unlock()  // defer 确保解锁
// 临界区

读写锁:

// Java
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();
rwLock.writeLock().lock();
// Go
var rwMu sync.RWMutex
rwMu.RLock()  // 读锁
rwMu.Lock()   // 写锁
坑点
  • Go 的 sync.Mutex 不可重入,同一 goroutine 二次 Lock 会死锁
  • Mutex / RWMutex 是值类型,千万不要被复制(go vet 会报)
  • 使用 defer Unlock() 几乎总是对的,但小心 defer 在大循环里的开销

3. 等待多个任务完成

Java: CountDownLatch

import java.util.concurrent.CountDownLatch;

CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            // 工作
        } finally {
            latch.countDown();
        }
    }).start();
}

latch.await();  // 等待所有完成

Go: sync.WaitGroup

import "sync"

var wg sync.WaitGroup

wg.Add(3)
for i := 0; i < 3; i++ {
    go func() {
        defer wg.Done()
        // 工作
    }()
}

wg.Wait()  // 等待所有完成
WaitGroup 三大铁律
  1. Add(N) 必须在 go 之前调用,绝不能放进 goroutine 内
  2. Done() 配 defer 使用,确保 panic 也能减计数
  3. 不要复制 WaitGroup,通过指针传递

4. 只执行一次

Java: 双重检查锁

public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

Go: sync.Once

import "sync"

var (
    instance *Singleton
    once     sync.Once
)

func GetInstance() *Singleton {
    once.Do(func() {
        instance = &Singleton{}
    })
    return instance
}
为什么 Go 更简单 sync.Once 内部已经处理了「双重检查 + 内存屏障」的所有细节,业务代码只需关心初始化逻辑。 这是 Go 标准库的典型风格 —— 把复杂藏到库里,把简单留给业务。

5. 条件变量

Java: Condition

import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

ReentrantLock lock = new ReentrantLock();
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();

// 生产者
lock.lock();
try {
    while (queue.size() == capacity) {
        notFull.await();
    }
    queue.put(item);
    notEmpty.signal();
} finally {
    lock.unlock();
}

Go: sync.Cond

import "sync"

var (
    mu      sync.Mutex
    cond    = sync.NewCond(&mu)
    queue   []int
    maxSize = 10
)

// 生产者
mu.Lock()
for len(queue) == maxSize {
    cond.Wait()
}
queue = append(queue, item)
cond.Signal()
mu.Unlock()

Go 的另一种方式:使用 Channel

// Channel 通常比 Cond 更简单易用
queue := make(chan int, 10)

// 生产者
queue <- item

// 消费者
item := <-queue
Go 圈子的共识 能用 Channel 解决的问题,就不要碰 sync.Cond。 Cond 在 Go 中是少数派,Go 团队甚至一度讨论过把它从标准库移走。

6. 并发安全的 Map

Java: ConcurrentHashMap

import java.util.concurrent.ConcurrentHashMap;

ConcurrentHashMap map = new ConcurrentHashMap<>();

map.put("key", "value");
String val = map.get("key");

Go: sync.Map

import "sync"

var m sync.Map

m.Store("key", "value")
val, ok := m.Load("key")

Go 的另一种方式:Mutex + Map

var (
    mu sync.RWMutex
    m  = make(map[string]string)
)

// 读
mu.RLock()
val := m["key"]
mu.RUnlock()

// 写
mu.Lock()
m["key"] = "value"
mu.Unlock()
选择建议
  • 读多写少 / 写后只读: sync.Map 性能最优 (设计场景)
  • 读写均衡 / 写多: sync.RWMutex + map 更可控
  • 需要 range 遍历: 普通 map 更直观,sync.Map 的 Range 不能修改边界

7. 线程池 vs Goroutine 池

Java: ExecutorService

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

ExecutorService pool = Executors.newFixedThreadPool(10);

for (int i = 0; i < 100; i++) {
    pool.submit(() -> {
        // 任务
    });
}

pool.shutdown();

Go: 通常不需要池!Goroutine 足够轻量

// 直接启动 Goroutine,通常不需要池
for i := 0; i < 100_000; i++ {
    go func() {
        // 任务
    }()
}

// 需要限制并发时,用 Channel 做信号量
sem := make(chan struct{}, 100)
for i := 0; i < 100_000; i++ {
    sem <- struct{}{}
    go func() {
        defer func() { <-sem }()
        // 任务
    }()
}

Goroutine 池实现(可选)

type Pool struct {
    tasks chan func()
    wg    sync.WaitGroup
}

func NewPool(size int) *Pool {
    p := &Pool{tasks: make(chan func())}
    p.wg.Add(size)
    for i := 0; i < size; i++ {
        go func() {
            defer p.wg.Done()
            for task := range p.tasks {
                task()
            }
        }()
    }
    return p
}
Java 直觉的陷阱 很多 Java 开发者一上来就想「Goroutine 一定要池化」。事实上, Goroutine 启动开销 ≈ 2~3 微秒,栈 2KB,GC 自动回收, 一台 16GB 服务器轻松撑住几十万 Goroutine。 只有当任务速率远高于资源限速时,才需要用 Channel 做限流。

8. Future / Promise vs Channel

Java: CompletableFuture

import java.util.concurrent.CompletableFuture;

CompletableFuture future = CompletableFuture.supplyAsync(() -> {
    return doSomething();
});

future.thenAccept(result -> {
    System.out.println(result);
});

String result = future.get();  // 阻塞等待

Go: Channel

ch := make(chan string, 1)

go func() {
    ch <- doSomething()
}()

// 阻塞等待
result := <-ch

// 或带超时
select {
case result := <-ch:
    fmt.Println(result)
case <-time.After(5 * time.Second):
    fmt.Println("timeout")
}
Future vs Channel Channel 比 Future 更通用 —— 一个 Channel 可以发多次值,可以 select 多路监听, 还能配合 context.Context 做超时和取消传播。

9. 原子操作

Java: AtomicInteger

import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger counter = new AtomicInteger(0);

counter.incrementAndGet();
int val = counter.get();

Go: sync/atomic

import "sync/atomic"

var counter int64

atomic.AddInt64(&counter, 1)
val := atomic.LoadInt64(&counter)

// Go 1.19+ 类型化原子,更安全
var c atomic.Int64
c.Add(1)
v := c.Load()
坑点 · 32 位对齐 在 32 位平台上,atomic.AddInt64 要求操作数 8 字节对齐, 否则会 panic。把 int64 字段放到 struct 最前面通常能避免这个坑; 或者直接用 Go 1.19+ 的 atomic.Int64 类型,运行时自动保证对齐。

11. 总结对比表

Java (java.util.concurrent) Go (sync / channel) 说明
ThreadGoroutineGoroutine 更轻量
ReentrantLocksync.MutexGo 用 defer 确保解锁
ReentrantReadWriteLocksync.RWMutex功能类似
CountDownLatchsync.WaitGroupWaitGroup 更易用
双重检查锁sync.OnceOnce 更安全简洁
Conditionsync.Cond / Channel优先用 Channel
ConcurrentHashMapsync.Map / RWMutex+map根据场景选择
ExecutorService通常不需要 / 工作池Goroutine 足够轻量
CompletableFutureChannelChannel 更灵活
AtomicIntegersync/atomic功能类似
ThreadLocalcontext.Context 传递Go 没有 ThreadLocal
Go 并发编程的核心三句话
  • Goroutine 是轻量级执行单元,启动如同函数调用
  • Channel 是同步与通信的一等公民,优先使用
  • sync 包是基本同步原语的兜底,Mutex / Once / WaitGroup 即可
