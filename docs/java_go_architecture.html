Java / Go 架构思路对比

本文目标 从架构设计思路层面对比 Java 和 Go,帮助 Java 开发者理解 Go 的设计哲学, 避免用 Java 思维写 Go 代码 —— 这是 Java→Go 迁移中最致命也是最常见的坑。

1. 面向对象(继承) vs 组合

Java 最深刻的心智模型就是「类型层次树」:一切类都来自 Object,通过 extends 建立父子关系,通过多态在父类指针下调用子类方法。Go 则没有继承,只有组合与 接口。

图 1 · Java 继承体系 vs Go 组合 + 接口体系

Java: 基于继承的 OOP

// Java: 继承
public class Animal {
    protected String name;
    public void eat() { /* ... */ }
}

public class Dog extends Animal {
    public void bark() { /* ... */ }
}
Java 特点
  • 类继承(单继承 + 多接口)
  • 多态通过继承体系实现
  • 设计模式大量使用继承 (Template Method、Decorator 等)

Go: 基于组合的设计

// Go: 组合而非继承
type Animal struct {
    Name string
}

func (a *Animal) Eat() { /* ... */ }

type Dog struct {
    Animal       // 匿名嵌入,类似继承但只是组合
    Breed string
}

func (d *Dog) Bark() { /* ... */ }
Go 特点
  • 没有继承,只有组合(struct 嵌入 struct)
  • 多态通过接口实现,接口靠方法集自动满足(鸭子类型)
  • 匿名嵌入只是语法糖,不是父子关系,不存在 instanceof 这种概念
心智迁移
  • 不要尝试用 struct 模拟类继承,Go 没有 super、没有 protected
  • 多用小接口,少用大接口(io.Reader、io.Writer 都只有 1 个方法)
  • 使用组合来复用代码,使用接口来定义行为契约

2. 异常处理 vs 值错误

Java: 异常机制

// Java: 异常
public User getUser(Long id) throws UserNotFoundException {
    User user = repository.findById(id);
    if (user == null) {
        throw new UserNotFoundException("User not found");
    }
    return user;
}

try {
    User user = getUser(123);
} catch (UserNotFoundException e) {
    // 处理异常
}
Java 特点
  • 异常分为 Checked / Unchecked
  • 异常会中断控制流,栈展开 (stack unwinding)
  • try-catch-finally 是核心处理结构

Go: 值错误

// Go: 多返回值 + error
func GetUser(id int64) (*User, error) {
    user := repository.FindByID(id)
    if user == nil {
        return nil, fmt.Errorf("user not found: %d", id)
    }
    return user, nil
}

user, err := GetUser(123)
if err != nil {
    // 处理错误
    return err
}
// 继续执行
Go 特点
  • 错误是普通的值(error 接口)
  • 多返回值返回错误,调用者必须显式检查
  • panic 只用于真正不可恢复的故障(类似 Java 的 Error / 严重 RuntimeException)
心智迁移
  • 不要用 panic 代替 error —— 不要把 Go 写成「带 try-catch 的 Java」
  • 错误是控制流的一部分,不是异常
  • 显式处理每个 error,不要 _ 忽略;Go 1.13+ 用 errors.Is / errors.As 包裹与解包

3. IoC 容器 vs 手动依赖注入

Java: Spring IoC 容器

// Java: Spring 自动注入
@Service
public class UserService {

    @Autowired
    private UserRepository repository;

    @Autowired
    private EmailService emailService;
}
Java 特点
  • 容器管理对象生命周期(单例 / 原型 / Session 等)
  • 自动注入依赖(@Autowired / 构造器注入 / Setter 注入)
  • 配置驱动 (XML / Java Config / Annotation)

Go: 手动依赖注入

// Go: 手动注入
type UserService struct {
    repo  UserRepository
    email EmailService
}

func NewUserService(repo UserRepository, email EmailService) *UserService {
    return &UserService{
        repo:  repo,
        email: email,
    }
}

// main 中组装
repo := NewUserRepository()
email := NewEmailService()
userService := NewUserService(repo, email)
Go 特点
  • 手动组装依赖,通常集中在 main 或 wire 文件中
  • 通过构造函数传递依赖,符合「明确优于隐式」
  • 有需要时可用 google/wire 做编译期 DI,而非运行期反射
心智迁移
  • 不要寻找 Spring 那样的 IoC 容器,Go 的「容器」就是 main()
  • 在 main 函数中组装所有依赖,自上而下,清晰可读
  • 构造函数应该是「纯」的,只做参数验证和赋值,不做副作用 IO

4. 线程池 vs Goroutine

Java: 线程池

// Java: 线程池管理
ExecutorService pool = Executors.newFixedThreadPool(10);

for (int i = 0; i < 100; i++) {
    pool.submit(() -> {
        // 任务
    });
}

pool.shutdown();
Java 特点
  • 线程开销大(默认栈 ~1MB),必须池化
  • 线程池大小需要谨慎配置(IO vs CPU 密集)
  • 上下文切换昂贵(由 OS 调度)

Go: Goroutine

// Go: 直接用 Goroutine
for i := 0; i < 100_000; i++ {
    go func() {
        // 任务
    }()
}

// 可选:用 Channel 或工作池限制并发
sem := make(chan struct{}, 100)
for i := 0; i < 100_000; i++ {
    sem <- struct{}{}
    go func() {
        defer func() { <-sem }()
        // 任务
    }()
}
Go 特点
  • Goroutine 开销极小(初始栈 2KB,动态伸缩),通常不需要池化
  • GOMAXPROCS 控制并行度(默认等于 CPU 核数)
  • Channel 用于同步、通信和控制 (CSP 模型)
心智迁移
  • 不要一上来就建 Goroutine 池(Java 直觉),先考虑直接 go func()
  • 需要限制并发时,用 Channel 做信号量 (Semaphore)
  • Goroutine 不是「免费」的:仍要管理生命周期、防泄漏 (用 context.Context)

5. Null 安全

Java: NullPointerException

// Java: NPE 风险
User user = getUser();
String name = user.getName();  // 如果 user 是 null,抛 NPE

// Java 8+: Optional
Optional userOpt = getUser();
userOpt.ifPresent(u -> { /* ... */ });

Go: nil 检查

// Go: 显式 nil 检查
user, err := GetUser()
if err != nil {
    return err
}
if user == nil {
    return errors.New("user not found")
}
name := user.Name  // 安全

// 接口 nil 的坑!
var u *User = nil
var i interface{} = u
fmt.Println(i == nil)  // false! 注意这个坑!
著名坑点 · 接口 nil Go 接口由 (type, value) 组成。给 interface{} 赋值一个「带类型的 nil 指针」时, 类型不是 nil,所以接口整体 != nil,这是 Java 开发者最常踩的坑之一。
心智迁移
  • 总是检查 error,Go 没有 NPE 抛出,但有 nil pointer dereference panic
  • 显式检查 nil;返回错误的函数通常会保证「err != nil 时其他返回值不可用」
  • 对外暴露 API 时,尽量避免返回带类型的 nil 接口

7. Go 的设计哲学

原则说明
简单优于复杂避免过度设计,保持代码简单直接
组合优于继承使用组合复用代码,而非继承
明确优于隐式显式处理错误,显式传递依赖
并发是一等公民Goroutine + Channel,CSP 模型
标准库优先优先使用标准库,避免不必要的依赖

8. Java 开发者的反模式(不要这样写 Go)

❌ 用 struct 模拟类继承 
// 不要这样!
type Base struct{}
type Derived struct { Base }
// 然后给 Derived 加一堆方法,试图覆盖 Base —— Go 没有真正的多态覆盖
❌ 忽略 error 
// 不要这样!
user, _ := GetUser()
// 一旦出错,你拿到的是一个空指针或半完整对象,生产环境一定出事
❌ 用 panic 代替 error 
// 不要这样!
if err != nil {
    panic(err)
}
// panic 用于不可恢复故障,正常业务错误请返回 error
❌ 过度设计 / 抽象层堆叠 
// 不要为了「将来灵活」而提前抽象出 Factory、Adapter、Strategy 三层
// Go 的灵魂是 KISS,等真有第二个实现时再抽象也来得及

9. 一句话总结

最重要的心智迁移 Java 是「类型 + 容器」的世界,通过 IoC、AOP、反射等魔法让代码看起来简洁;
Go 是「值 + 接口」的世界,所有东西都写在表面,没有隐藏控制流。
把 Go 当 Java 来写,只会写出又笨又难维护的代码。请拥抱简单。
