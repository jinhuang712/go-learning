5.2 · 崩溃与恢复 (Panic & Recover)

既然 Go 不提倡用异常 (Exception),那如果程序遇到真的无法继续执行的严重错误(比如空指针、数组越界、配置加载失败)该怎么办?

答案是:Panic (恐慌)。

5.2.1 Panic (引发恐慌)

panic 类似于 Java 中抛出 RuntimeException 或 Error。一旦调用 panic,正常的控制流会被中断,当前 goroutine 中的所有 defer 语句会按倒序执行,最后程序崩溃并打印堆栈跟踪。

什么时候用 Panic? 在微服务中,永远不要用 panic 处理业务逻辑错误(如密码错误、找不到数据)。 只有在不可恢复的程序 Bug(如必须要初始化的配置缺失、明显的开发者错误)时,才使用 panic。 
func mustLoadConfig(path string) Config {
    cfg, err := loadConfig(path)
    if err != nil {
        panic(fmt.Errorf("启动期配置加载失败: %w", err))
        // 这里 panic 是合理的:进程根本无法启动,fail fast
    }
    return cfg
}

5.2.2 Recover (恢复)

如果在 Web 服务中,某个请求触发了 panic,我们显然不希望整个微服务进程挂掉。我们需要一种机制捕获这个 panic,这就是 recover。

  • recover() 必须只在 defer 函数内部调用才有效。
  • 如果没有发生 panic,recover() 返回 nil。
  • 捕获到 panic 后,程序不会崩溃,而是从触发 panic 的函数正常返回,继续执行上层代码。
func safeCall() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    panicProneFunc()
    return nil
}

5.2.5 微服务中的最佳实践

在 Gin 或 Hertz 这种 Web 框架中,通常会有一个全局的 Recovery Middleware(恢复中间件)。它的作用就是在所有请求的最外层套一个 defer recover(),这样无论哪个业务开发人员写出了空指针 bug,都只会导致当前这个请求返回 HTTP 500,而不会导致整个微服务宕机。

// 典型的 Gin 风格 Recovery 中间件
func Recovery() gin.HandlerFunc {
    return func(c *gin.Context) {
        defer func() {
            if r := recover(); r != nil {
                // 1. 打印完整调用栈用于排查
                log.Printf("panic recovered: %v\n%s", r, debug.Stack())
                // 2. 上报监控
                metrics.PanicCounter.Inc()
                // 3. 返回 500
                c.AbortWithStatus(http.StatusInternalServerError)
            }
        }()
        c.Next()
    }
}

心智模型 把 recover 当成「整个微服务的最后一道防线」,而不是日常错误处理工具。 日常仍然用 error 返回值,只有那种「真的不应该走到这里」的情况才靠 panic + recover 兜底。
