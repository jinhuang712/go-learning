6.2 · 接口 nil 判断坑点

⚠ Java 转 Go 踩坑率 Top 1 这是 Java 转 Go 开发者踩坑率最高的 Top 1 问题。无数人在生产环境中因为这个问题导致错误被吞、服务异常。 理解它的底层 (type, value) 双指针原理是唯一根治办法。

6.2.1 底层原理:interface 是 (type, value) 双指针

一个接口变量等于 nil,当且仅当它的「类型指针」和「数据指针」都为 nil:

// 空接口底层结构
type eface struct {
    _type *type           // 类型指针
    data  unsafe.Pointer  // 数据指针
}

下面这张图直接展示了 4 种状态——只有左上角一种是真正的 nil:

图 · interface 的 (type, value) 双指针:case ② 是经典「错误被吞」坑——type 非 nil 但 data nil,整体 != nil

坑点 1:返回 nil 的具体类型指针给接口,导致错误判断失效

❌ 错误写法:返回 nil 的 *CustomError 给 error 接口 
type CustomError struct {
    Code int
    Msg  string
}

func (e *CustomError) Error() string {
    return fmt.Sprintf("code: %d, msg: %s", e.Code, e.Msg)
}

func GetUser(id int64) error {
    var err *CustomError
    if id <= 0 {
        err = &CustomError{Code: 400, Msg: "invalid id"}
    }
    // 当 id > 0 时,err 的类型是 *CustomError(不是 nil),数据是 nil
    // 所以返回的 error 接口不是 nil!
    return err
}

func main() {
    err := GetUser(1)
    if err != nil { // 这里永远为 true!即使没有错误
        log.Fatal("unexpected error: ", err) // 会输出: unexpected error: <nil>
    }
}
图 · 「错误被吞」根因:return err 把一个有类型的 nil 指针装进 error 接口,接口 != nil
✅ 正确写法:永远直接返回 nil,不要返回 nil 的具体类型指针 
func GetUser(id int64) error {
    if id <= 0 {
        return &CustomError{Code: 400, Msg: "invalid id"}
    }
    // 直接返回 nil,类型和数据都是 nil
    return nil
}

坑点 2:把 nil 的接口断言为具体类型,导致 panic

❌ 错误写法 
var i any = nil
var s string = i.(string)
// panic: interface conversion: interface {} is nil, not string
✅ 正确写法:使用 comma-ok 断言 
s, ok := i.(string)
if !ok {
    // 处理类型不匹配的情况
}

坑点 3:interface{} 和具体类型的 == 判断问题

var a int   = 0
var b int64 = 0
var ia any = a
var ib any = b

fmt.Println(ia == ib) // false!因为类型不同
原理 接口的 == 比较是 (type, value) 两元组都相等才相等。 int 和 int64 是不同的类型,即使 value 都是 0,接口也不相等。

6.2.2 防御性编程最佳实践

  1. 函数签名声明返回 error 时,函数内部要么直接 return nil,要么 return &ConcreteErr{...},千万不要声明 var e *ConcreteErr 然后 return e。
  2. 类型断言一律用 comma-ok,绝不裸用 v := i.(T)。
  3. 跨类型相等比较前,先用 reflect.TypeOf 或显式转换统一类型。

📝 练习题

  1. 修复 GetUser 函数的错误,让它能正确返回 nil error。
  2. 编写代码验证:只有当接口的类型和数据都为 nil时,接口才等于 nil。
  3. 解释为什么 fmt.Println(err) 会输出 <nil>,但 err != nil 却为 true。
