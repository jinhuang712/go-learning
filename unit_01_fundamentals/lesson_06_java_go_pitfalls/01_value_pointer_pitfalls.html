6.1 · 值/指针误用坑点

Java 默认对象引用、基本类型值传递,程序员从不需要主动选;Go 把选择权交给程序员,代价就是这一组高频坑。本节列举 3 个最常见的值/指针陷阱。

心智模型回顾 Java method(User u) 等价于 Go 的 method(u *User) (传引用副本); 而 Go 的 method(u User) 是整个结构体的完整拷贝——Java 里根本没有对应物。 混淆两者就会产生本节的坑。

坑点 1:方法接收者混用值和指针,导致状态修改失效

❌ 错误写法:值接收者修改状态无效 
type User struct {
    Name string
    Age  int
}

func (u User) SetAge(age int) {
    u.Age = age // 修改的是副本,原对象不变
}

func main() {
    u := User{Name: "Bob", Age: 20}
    u.SetAge(30)
    fmt.Println(u.Age) // 输出 20,不是 30!
}
✅ 正确写法:需要修改状态的方法必须用指针接收者 
func (u *User) SetAge(age int) {
    u.Age = age // 修改原对象
}

坑点 2:大结构体传值导致严重性能开销

Java 中对象默认传引用,没有这个问题。但 Go 中传值会拷贝整个结构体:

❌ 错误写法:大结构体传值 每次调用都拷贝几十 KB 内存,在热路径上会显著拖累 CPU 和 GC。 
type BigStruct struct {
    Field1 [1024]int
    Field2 [1024]string
    // 还有几十个其他字段...
}

func Process(s BigStruct) {
    // 每次调用 → 拷贝几十 KB
}
✅ 正确写法:大结构体传指针 只拷贝 8 字节地址。 
func Process(s *BigStruct) {
    // 8B 地址拷贝,内部按指针访问
}

经验阈值 工程实践:结构体超过 ~64 字节(大约 8 个字段)就优先考虑传指针。 但要注意,小结构体(time.Time 这样)传值反而更高效——CPU cache 友好,无需 GC 扫描。

坑点 3:值类型不能为 nil,误用导致判断错误

Java 中所有对象都可以为 null,但 Go 中值类型(int, string, struct 等)默认有零值,不能为 nil:

❌ 错误写法:无法区分「没传值」和「传了零值」 
type UserRequest struct {
    Age int // 前端没传的话默认是 0,无法区分是真的 0 还是没传
}
✅ 正确写法:需要区分零值和未传的场景用指针 
type UserRequest struct {
    Age *int // 没传的话是 nil,传了 0 的话是 *int=0
}

// 解析端
if req.Age != nil {
    // 字段确实被传了,即使值是 0
    fmt.Println("age =", *req.Age)
} else {
    // 字段未传,用默认值
}

真实场景 数据库 nullable 列(sql.NullInt64)、PATCH 半更新 API、Protobuf optional 字段—— 凡是要区分「不存在」vs 「零值」的场景,都得用指针或 sql.NullX 这类专门的 nullable 类型。
