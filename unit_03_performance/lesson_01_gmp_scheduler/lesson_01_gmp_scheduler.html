Lesson 1 · G-M-P 调度器模型与阻塞原理

本课程深入 Go runtime 内部,讲解 G-M-P 三元调度模型、Goroutine 的调度时机以及阻塞处理机制。理解了 G-M-P,你才能真正解释为什么 Go 能用几 KB 栈撑起百万级并发。

Java 对照 Java 一个 Thread 直接 1:1 映射到 OS 线程(NPTL),默认栈 1MB,创建上限受系统限制。 Go 使用 M:N 多对多调度: N 个 goroutine(G,栈 2KB 起)被多路复用到 M 个 OS 线程(M)上, 由调度器单元 P 在用户态完成 work-stealing,无需陷入内核,这就是 Go 高并发的根基。

🎯 G-M-P 三元模型核心示意

图 · G-M-P 三元调度模型: 多个 P 各持本地 G 队列,M 绑定 P 执行 G;空闲 P 触发 work-stealing 从其他 P 偷一半 G

为什么是 G-M-P,而不是 1:1 线程?

3 个根本动机
  1. 轻量: G 栈起步 2KB(线程默认 1-8MB),百万并发可行
  2. 用户态调度: P 在用户态完成 G 切换,无需系统调用,纳秒级开销
  3. 多核负载均衡: P 持有本地队列,M 间通过 work-stealing 自动平衡,无须全局锁

G · Goroutine

G 代表一个 goroutine,内部是一个 runtime.g 结构体,持有:

  • 栈: 起步 2KB,按需动态扩展/收缩(可达 GB 级)
  • 程序计数器 PC: 当前执行位置
  • 调度上下文 sched: 保存寄存器状态,被换下时用于恢复
  • 状态: _Grunnable / _Grunning / _Gwaiting / _Gdead 等

M · Machine (OS Thread)

M 代表一个真实的 OS 线程(runtime.m 结构体)。

  • M 必须绑定一个 P 才能执行 G(P 提供 G 与 mcache 等执行所需上下文)
  • 当 M 中的 G 发生系统调用阻塞时,Go runtime 会把 P 与 M 解绑,P 可挂到其他空闲 M,继续跑队列
  • M 的数量上限默认 10000(runtime.SetMaxThreads 可调)

P · Processor (调度器)

P 是 Go 调度的核心抽象,介于 G 和 M 之间。它的数量由 GOMAXPROCS 决定(默认 = CPU 核数)。

  • 每个 P 持有一个本地运行队列 LRQ(容量 256),减少锁竞争
  • P 持有 mcache(本地内存分配缓存),让内存分配无锁
  • 当 P 的 LRQ 空了 → 优先从 全局队列 GRQ 取;再不行则从其他 P 偷(work-stealing)

触发场景细节

  • 函数调用/栈扩容: 编译器在函数序言插入 morestack 检查,顺便检查抢占标志
  • 系统调用: 进入 entersyscall,P 立即解绑;返回时 exitsyscall 尝试拿回 P
  • runtime.Gosched(): 主动让出,当前 G 放回 LRQ 队尾
  • 同步原语: channel 收发、mutex 等待、sync.Cond 都会把 G 状态置为 _Gwaiting
  • 异步抢占 (Go 1.14+): sysmon 后台线程检测到 G 跑超过 10ms,通过信号(SIGURG)插入抢占点

🛑 阻塞原理与处理

两种阻塞 · 完全不同的处理
  • G 级阻塞 (channel/mutex): 只有 G 进入 _Gwaiting,M 不阻塞,P 可以继续跑队列中的其他 G
  • M 级阻塞 (系统调用): M 真正陷入内核被挂起,runtime 会把 P 摘下挂到新的 M,保证 P 不闲置

系统调用阻塞处理流程

sequenceDiagram autonumber participant G as G (用户 goroutine) participant M1 as M1 (绑定 P) participant P as P participant M2 as M2 (空闲) participant OS as OS Kernel G->>M1: 发起阻塞 syscall (read) M1->>OS: 陷入内核 Note over M1,OS: M1 阻塞在 OS 中 M1->>P: entersyscall: 解绑 P P-->>M2: runtime 唤醒/创建新 M2 接管 P M2->>P: 绑定 P,继续跑 LRQ 中的其他 G Note over M2,P: 整个 P 不闲置,继续高并发 OS-->>M1: syscall 返回 M1->>M1: exitsyscall M1->>P: 尝试拿回原 P alt 原 P 已被其他 M 占用 M1->>P: 拿其他空闲 P;若没有 → G 放 GRQ, M1 休眠 end

💻 探查 GMP 的代码示例

package main

import (
    "fmt"
    "runtime"
    "sync"
)

func main() {
    fmt.Println("GOMAXPROCS (P 数):", runtime.GOMAXPROCS(0))
    fmt.Println("NumCPU:", runtime.NumCPU())

    var wg sync.WaitGroup
    for i := 0; i < 4; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            fmt.Printf("goroutine %d running on M (thread)\n", id)
            // 主动让出,触发调度
            runtime.Gosched()
        }(i)
    }
    wg.Wait()

    fmt.Println("活跃 goroutine 数:", runtime.NumGoroutine())
}

⚠️ 生产环境坑点

坑点 1 · 长 CPU 循环占用 P 导致延迟 Go 1.14 之前没有异步抢占,纯计算 for 循环会霸占 P,其他 G 卡死。 Go 1.14+ 通过信号抢占已基本解决,但仍要谨慎: 把重 CPU 计算切片,定期 runtime.Gosched()。
坑点 2 · cgo / 系统调用过多导致 M 爆炸 每个阻塞 syscall 都可能临时拉起新 M,如果你大量并发执行 cgo 或阻塞 IO,M 数会冲到上限,内存激增。
解决: 用 workerpool 控制并发,把 IO 收敛到固定数量的 goroutine。
坑点 3 · GOMAXPROCS 在容器中识别错误 在 Docker/K8s 容器中,Go 1.5+ 默认读取宿主机核数,可能远大于容器 CPU 限制(cgroup),导致 P 过多 + 上下文切换。
解决: 用 go.uber.org/automaxprocs 自动根据 cgroup 设置 GOMAXPROCS。
