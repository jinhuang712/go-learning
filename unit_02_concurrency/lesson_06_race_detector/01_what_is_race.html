6.1 什么是数据竞争 (Data Race)

1. 一句话定义

数据竞争的精确定义 两个或多个 goroutine 同时访问同一个内存位置,其中至少一个是写操作,且这两次访问之间不存在 happens-before 关系。

这四个条件要同时满足。少了任何一个,都不构成 race:

  • 只有一个 goroutine 访问 → 不是 race(单线程串行)
  • 大家只读 → 不是 race(只读共享 OK)
  • 有写,但通过 Mutex / channel 建立了 happens-before → 不是 race(已同步)

2. 最小复现:count++ 的悲剧

func DemoDataRace() {
    var count int
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            count++   // ⚠️ 数据竞争!1000 个 goroutine 同时读写
        }()
    }
    wg.Wait()
    fmt.Println(count) // 期望 1000,实际每次都不一样
}

关键洞察:count++ 看起来是一行,实际是 3 个机器指令:

MOV count -> reg     # 1. 读到寄存器
ADD reg, 1           # 2. 自增
MOV reg -> count     # 3. 写回内存

3. 交错读写的时序示意

而且,这只是最良性的 race。更糟的情况:

  • 读到半写的指针(64 位机器上极小概率,但 32 位指针非原子时会发生)→ panic 或 segfault。
  • 编译器看到没有同步,可能把读移出循环(寄存器缓存),让你永远看不到对方的修改。
  • CPU 乱序执行 + store buffer 让写的可见顺序和代码顺序不一致。

4. Go 内存模型 · happens-before

「同时访问」这个词在分布式时钟下其实没有绝对意义。Go 用 happens-before 来定义「确定的先后关系」:

  • 同一个 goroutine 内部,代码顺序 = happens-before 顺序。
  • 跨 goroutine,必须通过同步原语建立 happens-before:
    • go f():go 语句 happens-before f 的第一行。
    • chan send 前的所有代码 happens-before 对应 receive 后的代码。
    • Mutex.Unlock happens-before 下一次 Lock 返回。
    • WaitGroup.Done happens-before Wait 返回。
    • sync.Once 的 Do(f) 中的 f happens-before 所有后续 Do 返回。
    • atomic.Store / atomic.Load 配合使用,建立 happens-before。

为什么 happens-before 是「桥」? 没有同步原语,两个 goroutine 的指令顺序完全由调度器和 CPU 决定—— A 写的 count = 5 可能永远不被 B 看到(寄存器缓存、store buffer 没刷新)。 有了 Unlock → Lock 这道屏障,Go runtime 保证内存可见性:Lock 返回时,Unlock 前的所有写入都对当前 goroutine 可见。

5. 用 -race 实战检测

在测试 / build / run 时加 -race 标志:

go test -race ./unit_02_concurrency/lesson_06_race_detector
go run  -race main.go
go build -race -o bin/app .

运行刚才那段 count++,会看到这样的输出:

==================
WARNING: DATA RACE
Read at 0x00c0000a4008 by goroutine 7:
  main.DemoDataRace.func1()
      race_detector.go:29 +0x39

Previous write at 0x00c0000a4008 by goroutine 6:
  main.DemoDataRace.func1()
      race_detector.go:29 +0x4e

Goroutine 7 (running) created at:
  main.DemoDataRace()
      race_detector.go:27 +0xc8
==================
race detector 怎么工作 race detector 基于 Google 的 ThreadSanitizer (TSAN):
  • 它给每次内存访问插桩,记录访问者 goroutine ID + 当前的「vector clock」(每个 goroutine 一个时钟)。
  • 每次同步操作(Unlock、channel send),更新 vector clock。
  • 检测两次访问的 clock 是否有 happens-before 关系,没有 + 至少一写 → 报告 race。

代价是 5-10x 内存、2-20x CPU。开发 / CI 阶段开,不要在生产环境开。

6. 修复数据竞争的 4 种手段

方案 A · Mutex(最直接)

var count int
var mu sync.Mutex

go func() {
    mu.Lock()
    count++
    mu.Unlock()
}()

方案 B · Atomic(最快)

var count int64

go func() {
    atomic.AddInt64(&count, 1)
}()

方案 C · Channel(最 Go-style)

ch := make(chan int, 1000)
for i := 0; i < 1000; i++ {
    go func() { ch <- 1 }()
}
var count int
for i := 0; i < 1000; i++ {
    count += <-ch
}

方案 D · 不可变(根除)

如果数据在 goroutine 启动后永不修改,就根本不会有 race。常见做法:

  • 启动前一次性算好,只读分发。
  • 每次更新都替换整个对象(配合 atomic.Value 做 publish)。
  • 函数式风格:用「返回新值」代替「修改旧值」。

7. 5 种典型 race 场景

  1. 未同步的 map 读写(Go map 本身不是并发安全的,会直接 panic)
  2. 结构体字段并发读写(尤其是包含 slice / pointer 的字段)
  3. 计数器非原子(count++ / ++count)
  4. 闭包变量捕获:for i := range xs { go f(i) } 中的 i 共享(Go 1.22 已修复)
  5. 切片 append 并发:append 可能触发底层数组 reallocate,多 goroutine append 同一 slice 等于读写同一 header

8. Race Detector 的局限

三个真相
  • 只能发现「执行到的」race。如果某段并发代码在测试中没跑到,race detector 永远不会报。所以压力测试 + 模糊测试是必要补充。
  • 性能代价大。生产开 -race 等于自杀,只在 CI / staging 开。
  • 对 sync/atomic 有特殊语义。把 atomic 和普通读写混用,race detector 仍能识别;但如果你用 unsafe.Pointer 绕过,它就盲了。

📝 练习题

  1. 把上面 DemoDataRace 直接跑一遍,再加上 -race 跑一遍,对比输出。
  2. 用 4 种方案(Mutex / atomic / channel / 不可变)分别修复,各自跑 -race 验证。
  3. 挑战:写一段「看起来在同步但其实没有」的代码——比如用 time.Sleep(100ms) 自以为足够等待——然后用 race detector 揭穿它。
