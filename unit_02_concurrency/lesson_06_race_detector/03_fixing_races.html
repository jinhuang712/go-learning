6.3 修复数据竞争 · 四种方案与选型

检测到 race 之后,你有 4 种主流修复方案:Mutex / RWMutex / atomic / channel。它们不是互相替代,而是有各自最优场景。选错了,代码要么慢、要么难读、要么仍然不安全。

1. 四种方案速查

方案核心思路典型场景性能档位
sync.Mutex临界区互斥通用,临界区有多步操作中
sync.RWMutex读写分级读多写少 + 临界区较大(>10μs)中高(读路径)

channel所有权转移数据流水线 / pipeline / 取消信号低-中(语义优先)

3. 方案一 · sync.Mutex(通用)

type Counter struct {
    mu    sync.Mutex
    count int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func (c *Counter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}

什么时候选它:不知道选什么时,先用 Mutex。临界区里有多步操作、多个字段、复杂条件判断,Mutex 永远不会错。

4. 方案二 · sync.RWMutex(读多写少)

type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.data[k]
    return v, ok
}

func (c *Cache) Set(k, v string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[k] = v
}
RWMutex 不是免费的午餐 RWMutex 内部维护 reader 计数,开销比 Mutex 大。判定标准:
临界区 < 1μs 或 写比例 > 25% → 用 Mutex 反而更快。
临界区 > 10μs 且 写比例 < 10% → RWMutex 优势明显。

5. 方案三 · sync/atomic(最快)

type Counter struct {
    count int64
}

func (c *Counter) Inc()           { atomic.AddInt64(&c.count, 1) }
func (c *Counter) Get() int64     { return atomic.LoadInt64(&c.count) }

// Go 1.19+ 新 API,推荐
type Counter2 struct {
    count atomic.Int64
}

func (c *Counter2) Inc()       { c.count.Add(1) }
func (c *Counter2) Get() int64 { return c.count.Load() }

什么时候选它:只有单字段简单操作(计数 / 标志位 / 引用切换)。一旦需要「读完再判断再写」的复合逻辑,要么用 CAS 循环、要么改用 Mutex。

6. 方案四 · channel(CSP 风格)

type Counter struct {
    ch chan int
}

func NewCounter() *Counter {
    c := &Counter{ch: make(chan int, 1)}
    c.ch <- 0
    return c
}

func (c *Counter) Inc() {
    n := <-c.ch
    n++
    c.ch <- n
}

func (c *Counter) Get() int {
    n := <-c.ch
    c.ch <- n
    return n
}
不要为了「Go 范儿」滥用 channel 上面这个 channel 计数器只是演示用——简单计数用 channel 比 Mutex 慢 10× 以上,而且语义更难读。channel 的最佳场景是数据所有权的流转(pipeline、生产者消费者、取消传播),不是「保护共享状态」。

7. 性能横向对比(直观感受)

package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

type MutexCounter struct {
    mu    sync.Mutex
    count int
}
func (c *MutexCounter) Inc() { c.mu.Lock(); c.count++; c.mu.Unlock() }
func (c *MutexCounter) Get() int { c.mu.Lock(); defer c.mu.Unlock(); return c.count }

type AtomicCounter struct{ count int64 }
func (c *AtomicCounter) Inc()        { atomic.AddInt64(&c.count, 1) }
func (c *AtomicCounter) Get() int64  { return atomic.LoadInt64(&c.count) }

type ChannelCounter struct{ ch chan int }
func NewChannelCounter() *ChannelCounter {
    c := &ChannelCounter{ch: make(chan int, 1)}
    c.ch <- 0
    return c
}
func (c *ChannelCounter) Inc()       { n := <-c.ch; n++; c.ch <- n }
func (c *ChannelCounter) Get() int   { n := <-c.ch; c.ch <- n; return n }

func main() {
    const N = 1_000_000

    mc := &MutexCounter{}
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < N; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); mc.Inc() }()
    }
    wg.Wait()
    fmt.Printf("Mutex:   %d, time: %v\n", mc.Get(), time.Since(start))

    ac := &AtomicCounter{}
    start = time.Now()
    for i := 0; i < N; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); ac.Inc() }()
    }
    wg.Wait()
    fmt.Printf("Atomic:  %d, time: %v\n", ac.Get(), time.Since(start))

    cc := NewChannelCounter()
    start = time.Now()
    for i := 0; i < 1000; i++ {  // 少跑 1000×
        wg.Add(1)
        go func() { defer wg.Done(); cc.Inc() }()
    }
    wg.Wait()
    fmt.Printf("Channel: %d, time: %v (only 1000 iters!)\n", cc.Get(), time.Since(start))
}

典型机器上的相对性能(仅供感受,实际数字看机器):

方案1M 次累加耗时相对慢度
atomic~30 ms1×
Mutex~200 ms~7×
RWMutex(纯写)~280 ms~9×
channel1k 次就 ~3 ms,1M 次 推算 >3 s~100×

8. Java 修复方案对照

GoJava说明
sync.Mutexsynchronized / ReentrantLock都是通用互斥
sync.RWMutexReentrantReadWriteLock都支持读写分级
sync/atomicAtomicInteger 等 / VarHandle都用 CPU CAS 指令
sync.MapConcurrentHashMapJava 的更通用,Go 的偏读多写少
channelBlockingQueue / DisruptorJava 没有「语言级 channel」,需要库
从 Java 思维切到 Go 的最大差异 Java 老兵的本能是「找一个并发集合类」(ConcurrentHashMap、CopyOnWriteArrayList),Go 的本能应该是先问「能不能用 channel 把共享变成传递?」 不行再用 Mutex/atomic。Rob Pike 的名言:「Don't communicate by sharing memory; share memory by communicating.」

9. 生产环境坑点

坑点 1:简单的计数器套上 Channel 上面 benchmark 显示 channel 计数比 atomic 慢 100×。简单的计数器永远应该用 atomic 或 Mutex,不要为了「看起来 Go-style」用 channel。
坑点 2:用 sync.Map 替代所有 map sync.Map 在写多读少时比 RWMutex+map 慢 2-3 倍。它真正擅长的是「键空间稳定 + 读绝对压倒写」(典型:微服务路由表、metric 标签 map)。
坑点 3:修完不跑 race detector 二次验证 
# ❌ 改完代码直接合并
git push origin fix/race-counter

# ✅ 加锁后必须用 race detector 再次确认
go test -race -count=3 ./...
git push origin fix/race-counter
Race 修复经常出现「修了 A 点忘了 B 点」的情况,-race -count=N 是最便宜的兜底。
坑点 4:用读锁包住会写的逻辑 
// ❌ 用 RLock 但里面其实改了状态
func (c *Cache) GetOrInit(k string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    if v, ok := c.data[k]; ok { return v }
    c.data[k] = compute(k)   // 💥 在读锁下写 map → race
    return c.data[k]
}
要么全程持写锁,要么用「双检查」模式:RLock 看 → 命中返回 / 没命中升级到 Lock 重新检查再写。

📝 练习题

练习 3.1 · 用三种方案修同一个 race

package main

import (
    "fmt"
    "sync"
)

func main() {
    var counter int
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++ // race
        }()
    }

    wg.Wait()
    fmt.Println("Counter:", counter)
}

验收标准:

  • Mutex 版本
  • atomic 版本
  • channel 版本
  • 三个版本都跑 go test -race 通过
  • 简单测量三个版本的性能差异(time.Since 或 Go benchmark)
