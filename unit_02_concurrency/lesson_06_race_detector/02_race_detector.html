6.2 Race Detector 用法 · -race 标志

Go 工具链内置了一个工业级的数据竞争检测器,基于 Google 的 ThreadSanitizer (TSan) 算法。只需要在 go run / build / test 上加 -race 标志,编译器会在每条内存访问指令上自动插入运行时探针,运行时追踪 happens-before 关系,发现 race 立刻打印告警。

1. 三种用法

# 运行单文件
go run -race main.go

# 跑测试(强烈推荐 CI 里常开)
go test -race ./...

# 编译带 race 的二进制(只在开发 / 灰度自检)
go build -race -o app

# vet 静态检测 + race 运行时检测 一起跑
go test -race -v -count=1 ./...

2. 原理 · -race 是如何工作的

Race detector 不是简单的「监控锁」,而是记录每次内存访问的 happens-before 向量时钟,看新访问是否与历史访问形成偏序。

关键概念:Happens-Before 通过什么建立? Go Memory Model 明确列出建立 happens-before 的方式:
  • 同一 G 内:程序顺序 (program order)
  • 锁配对:Unlock() happens-before 下一次 Lock()
  • channel:发送 happens-before 对应的接收完成
  • sync.Once:Do 内函数 happens-before 所有后续 Do 返回
  • WaitGroup:所有 Done() happens-before Wait() 返回
  • atomic 操作(顺序一致):Store happens-before 后续相同地址的 Load
  • go 语句:启动一个 G 前的所有操作 happens-before 这个 G 的开始

3. 如何解读输出

==================
WARNING: DATA RACE
Write at 0x00c0000ae008 by goroutine 7:                  ← 当前访问(写)
  main.main.func1()
      /path/main.go:15 +0x3a                              ← 出错的代码行

Previous write at 0x00c0000ae008 by goroutine 6:         ← 与之冲突的历史访问
  main.main.func1()
      /path/main.go:15 +0x3a

Goroutine 7 (running) created at:                        ← G 是从哪里启动的
  main.main()
      /path/main.go:13 +0x9d

Goroutine 6 (finished) created at:
  main.main()
      /path/main.go:13 +0x9d
==================
Found 1 data race(s)
exit status 66                                           ← 非零退出码,CI 会失败
关键字段含义
Write at 0x... / Read at 0x...当前冲突访问的内存地址 + 类型
Previous write/read对同一地址的另一次访问
栈帧 (main.func1...)访问发生的代码位置,精确到行号
Goroutine N (running/finished)那个 G 的状态以及它在哪里被 go 启动
退出码 66race 检测到时,默认进程以 66 退出。可用 GORACE="halt_on_error=0" 让程序继续

4. 在测试与 CI 中常态化

package counter_test

import (
    "sync"
    "testing"
)

func TestCounter_Race(t *testing.T) {
    var counter int
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++ // 等待 -race 发现
        }()
    }
    wg.Wait()
    if counter != 1000 {
        t.Errorf("Expected 1000, got %d", counter)
    }
}
go test -race -v -count=1 ./...
CI 接入建议
  • 把 go test -race ./... 加进 PR check,任何 race 都阻塞合并
  • 常跑 -race -count=5 增加调度多样性,提高 race 命中率
  • 用 GORACE="halt_on_error=1 log_path=stderr" 第一时间停下来看完整栈

6. 生产环境坑点

坑点 1:不在 CI 跑 -race 
# ❌ 只跑常规测试,race 永远发现不了
go test ./...

# ✅ 至少在主分支 / 夜间任务里常跑
go test -race -count=1 ./...
坑点 2:以为 -race 能找出所有问题 -race 是动态分析——只能检测实际跑到的代码路径上的竞争。如果你的并发分支没被测试触发,race 一辈子检测不到。
对策:写并发测试时主动用大循环 + runtime.Gosched() 让调度更激进;关键路径用 -count=5/10 重复多次。
坑点 3:把 -race 二进制上生产 
# ❌ 生产用 -race 编译,性能直接腰斩
go build -race -o server

# ✅ 生产用普通编译,只在开发 / 测试 / 灰度自检用 -race
go build -o server
插桩二进制的内存占用是普通版本 5-10 倍,CPU 大幅下降。除非用「灰度小流量 + 短时间」临时排查偶发问题,否则不要在生产开 race。
坑点 4:跑测试时忘了 -count=1 Go test 默认会缓存测试结果。如果你改完代码加了 -race 但忘加 -count=1,可能直接命中缓存,根本没真正跑。

练习 2.1 · 实战

  1. 写一个明显有 race 的程序(counter++ 在 1000 个 G 里并发),跑 go run -race,把输出贴出来逐行解释。
  2. 对应写一个 TestXxx,通过 go test -race 让 CI 失败,观察 exit status。

  1. Race detector 是如何工作的?它的核心算法依赖什么?
  2. 为什么 -race 能找到 race 但不能证明程序没有 race?用「动态分析 vs 静态分析」的角度回答。
  3. 列出 3 种建立 happens-before 关系的方式。
