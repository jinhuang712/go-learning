6.1 什么是数据竞争 (Data Race)

Go Memory Model 的形式定义:「A data race occurs when two memory accesses concur, at least one is a write, and they are not ordered by a happens-before relation.」

翻译成人话:两个 Goroutine 同时访问同一块内存,且至少有一个是写操作,中间又没有用锁 / channel / atomic 建立明确的先后关系,就发生了数据竞争。

1. 一个最经典的例子

var counter int

// G1
go func() { counter++ }()  // 读 counter, +1, 写回(三步)

// G2
go func() { counter++ }()  // 同样三步

// counter++ 不是原子的!
// 在汇编层面:
//   MOV  rax, [counter]
//   INC  rax
//   MOV  [counter], rax

Lost Update · 丢失更新的真实时序

下面的 sequenceDiagram 展示两个 G 并发执行 counter++ 时,如何「一起读到 0、一起算出 1、一起写回 1」,结果两次累加只剩一次效果。

counter participant G2 as Goroutine 2 Note over MEM: counter = 0 G1->>MEM: ① LOAD counter → r1=0 G2->>MEM: ② LOAD counter → r2=0 Note over G1,G2: 两个 G 都读到了 0! G1->>G1: ③ r1 = r1 + 1 → r1=1 G2->>G2: ④ r2 = r2 + 1 → r2=1 G1->>MEM: ⑤ STORE counter ← 1 G2->>MEM: ⑥ STORE counter ← 1 Note over MEM: counter = 1
(预期 2 · 丢失 1 次更新!)
图 · Lost Update:两个 Goroutine 交错执行 counter++,两次 +1 最后只产生 +1 效果
数据竞争 ≠ 偶发 bug 上面的时序必然会在某些调度下出现。你本地跑可能 99% 看起来「对」,因为 G1 大概率全部跑完才轮到 G2;但生产高并发 + 多核环境下,这种交错每秒发生上万次。

2. 为什么数据竞争这么危险

危害说明
结果不确定计数对不上、累加丢失、读到中间态
内存撕裂(torn write)非对齐 64 位写 / interface header 的两个字 / slice header 三字段,可能只更新一半
直接 panic原生 map 并发读写 → fatal error: concurrent map writes(不可 recover)
难以复现依赖具体调度时序,生产偶发,本地测不出
跨函数污染未初始化的指针 / 半初始化对象被别的 G 看到,触发 nil deref / 业务逻辑错乱
Go 的 map 并发读写 = 必 panic Go runtime 在 map 操作内部加了「写并发检测」——一旦发现两个 G 同时写,直接 fatal error 退出进程(不会被 recover 捕获)。这是 Go 强烈劝阻你用裸 map 做共享态的方式。

3. 三个最常见的踩坑场景

场景 A · 共享计数器

var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }()  // ❌ data race
}

场景 B · map 并发读写

var m = make(map[string]string)
go func() { m["k"] = "v" }()       // 写
fmt.Println(m["k"])                // 读
// ❌ 大概率 panic: concurrent map read and map write

场景 C · slice append 并发

var s []int
go func() { s = append(s, 1) }()  // 可能触发底层数组扩容 + 替换 header
fmt.Println(s[0])                 // ❌ 可能读到旧 header 指向被释放的数组

// Java 同样的 Lost Update 例子
public class Counter {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) count++;
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) count++;
        });
        t1.start(); t2.start();
        t1.join();  t2.join();
        System.out.println("Count: " + count);  // 不一定是 20000
    }
}
Java volatile vs Go atomic Java volatile 解决「可见性 + 禁止重排序」,但不保证复合操作原子——volatile int x; x++; 仍然有竞争。等价于 Go 的:用 atomic.Load/Store 解决可见性,但 x = atomic.Load + 1; atomic.Store 依然有 race;真要原子自增必须用 atomic.Add 或 CAS 循环。

5. 用 race detector 看一眼

package main

import (
    "fmt"
    "sync"
)

func main() {
    var counter int
    var wg sync.WaitGroup
    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++ // race
        }()
    }
    wg.Wait()
    fmt.Println("Counter:", counter)
}
go run -race main.go

6. 生产环境坑点

坑点 1:以为「单次写 + 多次读」是安全的 
var config string

go func() {
    config = loadFromRemote()   // 写一次
}()

fmt.Println(config)             // 多次读,看起来「只读不写不会乱吧?」
仍然是 data race。没有 happens-before 时,读侧可能看到部分更新的字符串 header、或永远看不到新值(被 CPU cache 卡住)。
坑点 2:map 并发读写 = 必 panic 
var m = make(map[string]string)
go func() { m["k"] = "v" }()
fmt.Println(m["k"])
// fatal error: concurrent map read and map write
不可恢复,直接进程退出。改用 sync.Map 或 RWMutex+map。
坑点 3:slice 并发 append 看似只「写」一个变量,实际危险 s = append(s, x) 由三个字段(ptr/len/cap)的写组成。并发 append 可能扩容后 ptr 指向旧底层数组,产生丢数据 / 看到中间态。

📝 练习题

练习 1.1 · 找出所有 race 点

package main

import (
    "sync"
    "time"
)

type User struct {
    Name string
    Age  int
}

var user *User

func main() {
    var wg sync.WaitGroup

    wg.Add(1)
    go func() {
        defer wg.Done()
        time.Sleep(100 * time.Millisecond)
        user = &User{Name: "Alice", Age: 30}
    }()

    wg.Add(1)
    go func() {
        defer wg.Done()
        if user != nil {
            println("User:", user.Name)
        }
    }()

    wg.Wait()
}

验收标准:

  • 说出全部 race 点(共享变量 user 的读写)
  • 解释为什么 time.Sleep 不能建立 happens-before 关系
  • 列举可能的具体问题(读到 nil / 读到半初始化对象 / cache 不同步)
