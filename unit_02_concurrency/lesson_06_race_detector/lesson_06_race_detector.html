Lesson 6 · Race Detector 数据竞争检测实战

并发编程的「头号刺客」是数据竞争(data race)——多个 Goroutine 在没有同步的前提下并发读写同一块内存,只要至少有一个是写,结果就完全不可预测。本课不仅讲什么是数据竞争,更重要的是教会你用 Go 内置的 -race 工具主动发现并修复它。

学习目标

能力验收标准
识别数据竞争看代码就能找出未同步的共享变量读写,说出可能的具体后果
使用 race detector会用 go run -race、go test -race,能解读输出栈帧
选择修复方案能根据「读写比例 / 临界区大小 / 通信 vs 共享」选 Mutex/RWMutex/atomic/channel
验证修复修复后用 -race 二次验证,并理解它不能证明「无 race」只能证明「有 race」

Java 心智迁移速查

JMM / volatile / ThreadSanitizer 三件套对照
  • JMM 的 happens-before ≈ Go Memory Model 的 happens-before——都是定义「一个写对另一个读何时可见」的形式规则
  • Java volatile ≈ Go 的 sync/atomic + 隐式 memory order(Go 没有 volatile 关键字)
  • Java ThreadSanitizer / Helgrind / FindBugs ≈ Go -race——但 Go 内置且开销低 2-5 倍,生态接入更友好
  • Java 的 synchronized 块 ≈ Go 的 defer mu.Unlock(); mu.Lock() 配对——但 Java 不可能忘记释放,Go 必须 defer 兜底

本课重点速览

  • 定义:两个 G 并发访问同一内存,至少一个是写,且没有 happens-before 关系 → data race
  • 危害:不仅是「结果偶尔错」,还可能是内存撕裂(torn read)、map panic、未初始化指针 deref crash
  • 检测:-race 编译期插桩 + 运行时 vector clock 追踪 happens-before,运行时开销 2-10x、内存 5-10x
  • 修复:简单计数 → atomic,通用临界区 → Mutex,读多写少 → RWMutex,数据所有权流转 → channel
  • 原则:「Don't communicate by sharing memory; share memory by communicating.」(Rob Pike)

运行方式

# 单文件检测
go run -race main.go

# 整个包测试 + race 检测
go test -race ./...

# 编译带 race 的二进制(只用于开发环境)
go build -race -o app

# 本课程示例
go test -race ./unit_02_concurrency/lesson_06_race_detector/code
不要在生产部署 -race 编译的二进制 插桩版本的内存占用是普通版本的 5-10 倍,CPU 也明显变慢。-race 是开发 / 测试 / 灰度自检工具,生产部署必须用普通 go build。
