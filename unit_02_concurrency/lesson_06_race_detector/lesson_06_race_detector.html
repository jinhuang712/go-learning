Lesson 6 · Race Detector 数据竞争检测实战

数据竞争(Data Race)是并发程序里最隐蔽、最致命的 bug:它可能让你的代码看起来工作了一万次,然后某次生产环境流量一上来,直接产生脏数据、panic、甚至运行时 corruption。 Go 语言把这个问题列为「未定义行为」(undefined behavior),并提供了官方 race detector,让你能在测试阶段把它揪出来。

官方定义 当两个或多个 goroutine 同时访问同一个变量,且至少有一个是写操作, 并且之间没有 happens-before 关系时——这就是数据竞争。 Go 内存模型规定:有 race 的程序行为未定义,任何输出都不构成 bug,也不构成正确。
Java 对比 · 为什么 Go 把这件事说得这么严

Java 也有数据竞争,但 JMM(Java Memory Model)定义得相对宽松:

  • Java 默认有 reference 原子性、final 字段安全发布等保障,有 race 时还可能「凑合工作」。
  • JVM 自带 -XX:+UseConcMarkSweepGC 等,有时会让 race 隐式生效。
  • Java 检测工具(ThreadSanitizer、FindBugs)是第三方,默认不开。

Go 把所有 race 列为 UB,但作为补偿,把 race detector 内置在 toolchain 里——一个 -race flag 搞定。这是 Go 在「易用性」和「严格性」之间的一次精彩平衡。

🚀 运行方式

# 运行单元测试
go test ./unit_02_concurrency/lesson_06_race_detector

# 启用 race detector(必看)
go test -race ./unit_02_concurrency/lesson_06_race_detector

# 也可以在 build / run 阶段开启
go build -race -o bin/app .
go run -race main.go

🎯 本课核心收获

  • 能用一句话定义「数据竞争」:多 goroutine、共享变量、至少一写、无 happens-before。
  • 会用 go test -race 在 CI 中守住底线,而不是等线上炸。
  • 理解 4 种修复手段的取舍:Mutex / Channel / Atomic / 不可变。
  • 知道 race detector 的 3 个局限:只检测被实际执行的路径、CPU/内存 5-10x、和 sync/atomic 配合微妙。
