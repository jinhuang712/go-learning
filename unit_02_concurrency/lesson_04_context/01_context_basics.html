4.1 Context 基础

context.Context 是 Go 标准库 context 包提供的接口类型,设计目的非常单纯——在 Goroutine 之间安全地传递「请求级别」的三类信号:取消(cancel)、超时(deadline)、元数据(value)。它是整个 Go 微服务调用链的「神经系统」。

1. Context 接口的四个方法

type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done()    <-chan struct{}
    Err()     error
    Value(key any) any
}

四个方法对应 Context 的 4 大语义,记住它就掌握了 Context 的本质:

图 · Context 接口的 4 个方法以及它们在工程上的对应用途
  • Deadline() — 返回 Context 的截止时间,如果没有 deadline,ok = false。下游可以据此决策「还要不要发 RPC、要不要给数据库设短一些的超时」。
  • Done() — 返回一个只读 channel。当 Context 被取消或超时,channel 会被关闭。关闭 channel 是 Go 中最经典的「广播取消信号」机制:任何在 <-ctx.Done() 上阻塞的 Goroutine 都会立即被唤醒。
  • Err() — 在 Done() 关闭之后,告知为什么被关闭:context.Canceled 表示主动调 cancel(),context.DeadlineExceeded 表示超时。
  • Value(key) — 取请求级元数据(traceID、userID)。不要用它传业务参数!

2. 根 Context:Background() vs TODO()

Context 必须从一个「根」开始派生。标准库提供两个根:

函数返回值语义典型场景
context.Background() 非 nil 的空 Context 「程序的顶层 Context」,永远不会被取消、没有 deadline、没有 value main()、HTTP server 启动、init 阶段
context.TODO() 同样是空 Context 「我也不知道这里该传什么,占个坑」 重构、新写代码暂时还没想清楚 ctx 来源
语义差异 ≠ 行为差异 Background() 和 TODO() 的内部实现完全相同(都是 emptyCtx)。它们的差异只存在于代码可读性:静态分析工具(如 go vet、IDE)会把 TODO() 提示成「待完成」,提醒你日后替换为真实 ctx。

3. Java 对照:为什么 Go 需要 Context?

Java 等价物拼图 Go 一个 ctx 在 Java 里需要拼接 4 个不同的东西:
  • ThreadLocal<T> / InheritableThreadLocal<T> — 元数据传递
  • Future.cancel(true) / Thread.interrupt() — 取消信号
  • Future.get(timeout) / CompletableFuture.orTimeout() — 超时
  • MDC(Mapped Diagnostic Context,SLF4J) — 日志 traceID 透传
Java 程序员最痛的 ThreadLocal 内存泄漏、线程池场景下值丢失,在 Go 里都不存在——因为 Context 显式作为函数参数。

Java 代码对照

// Java:用 ThreadLocal + Future 凑出 Context 的能力
public class JavaContextExample {
    private static final ThreadLocal<String> USER_ID = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        USER_ID.set("user-123");

        Future<String> future = executor.submit(() -> {
            // 在线程池里,USER_ID.get() 可能是 null!
            String userId = USER_ID.get();
            return "处理用户: " + userId;
        });

        try {
            String result = future.get(5, TimeUnit.SECONDS);
            System.out.println(result);
        } catch (TimeoutException e) {
            future.cancel(true);
            System.out.println("超时");
        }
        executor.shutdown();
    }
}
// Go:Context 一气呵成
package main

import (
    "context"
    "fmt"
    "time"
)

type userIDKey struct{}

func main() {
    ctx := context.Background()

    // 1. 注入元数据
    ctx = context.WithValue(ctx, userIDKey{}, "user-123")

    // 2. 注入超时
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()

    done := make(chan string, 1)
    go func() {
        userID := ctx.Value(userIDKey{}).(string)
        done <- fmt.Sprintf("处理用户: %s", userID)
    }()

    select {
    case result := <-done:
        fmt.Println(result)
    case <-ctx.Done():
        fmt.Println("超时或取消:", ctx.Err())
    }
}

4. 最基本的「取消模式」

❌ 错误写法:不接收 Context,无法取消

func doWork() {
    for {
        time.Sleep(1 * time.Second)
        fmt.Println("工作中...")
    }
}

func main() {
    go doWork()
    time.Sleep(3 * time.Second)
    // 此时 doWork 的 Goroutine 已经成了「失联的孤儿」,
    // 没有任何办法让它停下来 —— 直到进程退出。
}

✅ 正确写法:接收 Context,监听 Done()

func doWork(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            fmt.Println("收到取消信号,退出:", ctx.Err())
            return
        case <-time.After(1 * time.Second):
            fmt.Println("工作中...")
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    go doWork(ctx)

    time.Sleep(3 * time.Second)
    cancel() // 广播取消信号
    time.Sleep(500 * time.Millisecond)
}
心智模型:Context 是「请求的契约」 把 ctx 想象成「这个请求的生命周期合同」——它告诉每一层调用者:「这个请求的预算是多少、是否还在进行中、归属于谁」。一旦合同失效(取消/超时),所有下游都应该尽快撤退。

5. Background() vs TODO() 演示

package main

import (
    "context"
    "fmt"
)

func main() {
    ctx1 := context.Background()
    fmt.Println("Background():", ctx1) // context.Background

    ctx2 := context.TODO()
    fmt.Println("TODO():", ctx2)        // context.TODO

    // 内部都是 emptyCtx,但语义不同
    // 推荐:程序入口用 Background(),临时占位用 TODO()
}

6. 生产环境坑点提示

坑点 1:Context 不作为第一个参数 
// ❌ 错误:Context 不是第一个参数
func doWork(userID string, ctx context.Context) { /* ... */ }

// ✅ 正确:Context 永远是第一个参数,且命名 ctx
func doWork(ctx context.Context, userID string) { /* ... */ }
Go 团队、所有主流框架(grpc-go、net/http、database/sql)都遵循这个约定。go vet 也会对此发出警告。
坑点 2:把 Context 存进结构体 
// ❌ 错误:把 ctx 当成 struct 字段保存
type Worker struct {
    ctx context.Context // 不要!
}

// ✅ 正确:每次方法调用传入
type Worker struct{}
func (w *Worker) DoWork(ctx context.Context) { /* ... */ }
结构体常被多个请求共用,一个请求的 ctx 不应该污染其它请求。这条规则在官方 context 包文档开篇就强调过。
坑点 3:忘记 defer cancel() 
// ❌ 错误:cancel 函数被丢弃,timer 资源泄漏
ctx, _ := context.WithTimeout(parent, 5*time.Second)

// ✅ 正确:总是 defer cancel(),即使函数正常返回也要调用
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel()
go vet 的 lostcancel 分析器会检测这个错误。即使 ctx 已经因超时被取消,cancel() 也必须调用,否则定时器和子节点引用不会被释放。
