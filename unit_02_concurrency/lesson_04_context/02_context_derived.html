4.2 派生 Context (With* 家族)

Context 是不可变(immutable)的——你无法修改一个现存的 Context。所有「添加 cancel / timeout / value」的操作,都是通过 WithXxx(parent, ...) (Context, CancelFunc) 函数派生出一个新 Context。这与函数式编程的「不可变数据结构 + 复制」如出一辙。

1. 4 个派生函数

函数派生出什么典型用途
WithCancel(parent)可手动 cancel 的子 ctx用户主动中断、提前结束
WithTimeout(parent, d)带相对超时的子 ctx「这个 RPC 最多等 2 秒」
WithDeadline(parent, t)带绝对截止时间的子 ctx「全链路必须 14:00:00 之前结束」
WithValue(parent, k, v)携带 KV 元数据的子 ctxtraceID、userID、deviceID 透传

2. Context 是一棵树:派生关系图(必看)

每一次 WithXxx 都在父 Context 上「长出」一个新节点,形成一棵有向树。父节点取消 → 全部子孙节点取消(级联取消),反之子节点取消不会影响父节点。

图 · Context tree:从 Background 派生出 cancel/timeout/value 节点,叶子节点是真正干活的 Goroutine
级联取消的关键规则
  • 父取消 → 所有后代 ctx.Done() 全部关闭
  • 子取消 → 仅子树受影响,父和兄弟不受影响
  • 派生时取「较紧」的 deadline:WithDeadline(parent, t) 如果 t 比 parent 的 deadline 还晚,会被自动收紧

3. WithCancel:可手动取消

func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d: 收到取消信号,退出: %v\n", id, ctx.Err())
            return
        case <-time.After(500 * time.Millisecond):
            fmt.Printf("Worker %d: 工作中...\n", id)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    for i := 1; i <= 3; i++ {
        go worker(ctx, i)
    }

    time.Sleep(2 * time.Second)
    fmt.Println("发送取消信号...")
    cancel() // 一次 cancel,3 个 worker 全部退出

    time.Sleep(1 * time.Second)
}

4. WithTimeout / WithDeadline

func slowOp(ctx context.Context) string {
    select {
    case <-time.After(2 * time.Second):
        return "操作完成"
    case <-ctx.Done():
        return fmt.Sprintf("操作被取消: %v", ctx.Err())
    }
}

func main() {
    ctx := context.Background()

    // WithTimeout:相对超时(从现在开始 1s 后过期)
    ctx1, cancel1 := context.WithTimeout(ctx, 1*time.Second)
    defer cancel1()
    fmt.Println(slowOp(ctx1)) // → context deadline exceeded

    // WithDeadline:绝对时间点(从某个固定时刻过期)
    deadline := time.Now().Add(1 * time.Second)
    ctx2, cancel2 := context.WithDeadline(ctx, deadline)
    defer cancel2()
    fmt.Println(slowOp(ctx2))
}
什么时候用 WithDeadline? 微服务调用链需要「全链路截止时间」时:网关在请求一进来就 WithDeadline(now + 3s),下游每层调用都自动继承,即使你嵌套 WithTimeout(ctx, 5s),Go 会自动取更紧的那个。这是 Java 里非常难做到的——Java 各层 SDK 通常只支持本层的 connect / read timeout。

5. WithValue:请求级元数据

// 1. key 类型用空结构体,避免冲突 + 零内存
type userKey struct{}
type traceKey struct{}

func handle(ctx context.Context) {
    userID := ctx.Value(userKey{})
    traceID := ctx.Value(traceKey{})
    fmt.Printf("处理: user=%v, trace=%v\n", userID, traceID)

    downstream(ctx) // ctx 透传,下游也能取到
}

func downstream(ctx context.Context) {
    fmt.Printf("下游: user=%v\n", ctx.Value(userKey{}))
}

func main() {
    ctx := context.Background()
    ctx = context.WithValue(ctx, userKey{}, "user-123")
    ctx = context.WithValue(ctx, traceKey{}, "trace-456")
    handle(ctx)
}

6. Java 对照:ThreadLocal vs WithValue

两种「上下文」的本质差异 ThreadLocal 把数据塞到「线程对象」上,在异步 / 线程池场景下会丢失(必须用 TransmittableThreadLocal 或 MDC 装饰任务)。
WithValue 把数据塞到「Context 树」上,只要 ctx 被显式传递,就永远不会丢失。
维度Java ThreadLocalGo WithValue
存储位置当前 Thread 对象Context 链(链表 / 树)
异步传递需要 TransmittableThreadLocal / 装饰原生支持(显式传)
内存泄露风险必须手动 remove(),否则线程池会泄漏随 ctx 生命周期回收,无需手动清理
作用域线程级请求级
性能HashMap 查找 O(1)链表线性查找 O(n),n=链长度
典型滥用用 ThreadLocal 当全局变量用 WithValue 当函数参数
 
// Java:ThreadLocal + Future 凑超时 + 取消 + 元数据
public class JavaDerivedContext {
    private static final ThreadLocal<String> USER_ID = new ThreadLocal<>();
    private static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(3);

        USER_ID.set("user-123");
        TRACE_ID.set("trace-456");

        Future<String> future = executor.submit(() -> {
            // ⚠ 线程池中 USER_ID.get() 可能为 null!
            String userId = USER_ID.get();
            String traceId = TRACE_ID.get();
            try {
                Thread.sleep(2000);
                return "OK: " + userId;
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return "interrupted";
            }
        });

        try {
            System.out.println(future.get(1, TimeUnit.SECONDS));
        } catch (TimeoutException e) {
            future.cancel(true);
        }
        executor.shutdown();
    }
}
// Go:Context 自然搞定
type userIDKey struct{}
type traceIDKey struct{}

func main() {
    ctx := context.Background()
    ctx = context.WithValue(ctx, userIDKey{}, "user-123")
    ctx = context.WithValue(ctx, traceIDKey{}, "trace-456")
    ctx, cancel := context.WithTimeout(ctx, 1*time.Second)
    defer cancel()

    done := make(chan string, 1)
    go func() {
        userID  := ctx.Value(userIDKey{}).(string)
        traceID := ctx.Value(traceIDKey{}).(string)

        select {
        case <-time.After(2 * time.Second):
            done <- fmt.Sprintf("OK: %s (trace: %s)", userID, traceID)
        case <-ctx.Done():
            done <- fmt.Sprintf("超时或取消: %v", ctx.Err())
        }
    }()

    select {
    case r := <-done:
        fmt.Println(r)
    case <-ctx.Done():
        fmt.Println("主 ctx 超时或取消")
    }
}

7. 生产环境坑点提示

坑点 1:WithValue 用 string 作 key 
// ❌ 错误:用 string 容易冲突(不同包用了同名 key)
ctx = context.WithValue(ctx, "user-id", "123")

// ✅ 正确:自定义类型作 key
type userIDKey struct{}
ctx = context.WithValue(ctx, userIDKey{}, "123")
go vet 的 contextkeys 检查会对 string key 报警。最佳实践是空结构体类型:零内存占用、类型唯一、包私有。
坑点 2:忘记 defer cancel() WithCancel/WithTimeout/WithDeadline 三个函数都返回 (ctx, cancel)。即使 ctx 已经超时被自动取消,你仍然必须调用 cancel(),否则 timer、子节点引用不会被释放。go vet 会报 lostcancel。
坑点 3:WithValue 存大对象 Context 链查找是 O(n) 线性扫描,你存的对象越大、链越长,性能越差。WithValue 只能存请求级元数据(traceID、userID、authToken),业务参数请走函数参数。

📝 练习题

  1. 用 WithCancel 派生一个父 ctx,启动 3 个 worker。在主 Goroutine sleep 2s 后调用 cancel(),验证 3 个 worker 都能优雅退出。
  2. 嵌套调用:先 WithTimeout(ctx, 5s),再 WithTimeout(ctx, 1s)。打印 Deadline() 看看实际截止时间。
  3. 概念题:为什么 WithValue 的 key 应该用自定义类型而不是 string?这种设计避免了什么问题?
