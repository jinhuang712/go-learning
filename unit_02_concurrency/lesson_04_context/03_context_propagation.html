4.3 Context 传播最佳实践

本节聚焦工程化:如何让 Context 在一个真实微服务的「HTTP 入口 → middleware → handler → service → DB / RPC / cache」链路中正确传递、何时派生、何时不应该派生、key 类型怎么设计才不会污染其它模块。

1. Context 跨服务级联传播(必看时序图)

一次外部请求进来,Context 是这样传递的:网关 / API gateway 收到 HTTP 请求 → middleware 注入 traceID + 超时 → handler 派生子 ctx → 并发调用多个下游服务。一旦客户端取消(或网关超时),取消信号会通过 Done() 通道广播到所有正在执行的下游调用。

图 · Context 在 HTTP 请求 → 下游服务的级联传播,以及取消信号如何广播到所有 in-flight 调用
「广播取消」靠的是关闭 channel ctx.Done() 返回的是同一个 chan struct{} ——一旦关闭,所有在它上面 select 的 Goroutine 同时被唤醒。这是 Go 最优雅的「fan-out cancellation」机制,Java 里需要 AtomicBoolean isCancelled + 各处轮询 才能凑出类似效果。

2. Java vs Go:HTTP 请求处理对比

Servlet + ThreadLocal 的痛 Spring MVC 用 HandlerInterceptor + ThreadLocal 注入用户上下文,问题:
  • 必须在 afterCompletion 里 remove(),否则线程复用时上下文会污染下一个请求
  • 异步处理(@Async / CompletableFuture)中,ThreadLocal 会丢失
  • Servlet 规范没有标准的「请求级取消」机制,只能依赖客户端关闭连接 + HttpServletRequest.isAsyncStarted() 轮询
Go 的 r.Context() + r.WithContext(ctx) 一气呵成,且 http.Server 在客户端断连时自动 cancel request 的 ctx。

Java(Spring Boot + ThreadLocal)

@Component
public class UserInterceptor implements HandlerInterceptor {
    public static final ThreadLocal<String> USER_ID = new ThreadLocal<>();

    @Override
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res, Object h) {
        USER_ID.set(req.getHeader("X-User-ID"));
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req,
                                HttpServletResponse res,
                                Object h, Exception ex) {
        USER_ID.remove(); // ⚠ 漏调 = 线程池内存泄漏
    }
}

@RestController
public class UserController {
    @GetMapping("/user")
    public String getUser() {
        return "User: " + UserInterceptor.USER_ID.get();
    }
}

Go(net/http + Context)

package main

import (
    "context"
    "net/http"
    "time"
)

type userIDKey struct{}
type traceIDKey struct{}

// Middleware 注入 user/trace + 设置整体超时
func userMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()
        ctx = context.WithValue(ctx, userIDKey{},  r.Header.Get("X-User-ID"))
        ctx = context.WithValue(ctx, traceIDKey{}, r.Header.Get("X-Trace-ID"))

        ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
        defer cancel()

        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func userHandler(w http.ResponseWriter, r *http.Request) {
    userID := r.Context().Value(userIDKey{}).(string)
    w.Write([]byte("User: " + userID))
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/user", userHandler)
    http.ListenAndServe(":8080", userMiddleware(mux))
}

3. 规则一:Context 总是第一个参数

// ✅ 正确:ctx 第一个,且命名 ctx
func processRequest(ctx context.Context, reqID string) error { /* ... */ }

// ❌ 错误:ctx 不在第一位
func processRequest(reqID string, ctx context.Context) error { /* ... */ }

这是 Go 团队和所有主流标准库 / 框架 (grpc-go、net/http、database/sql、aws-sdk-go) 都遵循的语言级约定。go vet 也会强制检查。

4. 规则二:不要把 Context 存进结构体

// ❌ 错误:把 ctx 存为 struct 字段
type BadService struct {
    ctx context.Context  // 危险!
    db  *Database
}
func (s *BadService) Query() { /* 用 s.ctx */ }

// ✅ 正确:每次方法调用都接收 ctx
type GoodService struct {
    db *Database
}
func (s *GoodService) Query(ctx context.Context) { /* 用传入的 ctx */ }
为什么不能存 Service 里? Service 实例在 HTTP server 启动时只创建一次,会被多个并发请求共用。如果第一个请求把它的 ctx 存进去,第二个请求会复用这个已经过期 / 已取消的 ctx,行为完全错乱。
官方 context 包文档开篇就有这一条:「Do not store Contexts inside a struct type; instead, pass a Context explicitly to each function that needs it.」

5. 规则三:WithValue 的 key 用自定义类型

// ❌ 错误:用 string 作 key,容易跨包冲突
ctx = context.WithValue(ctx, "user-id", "123")

// ✅ 正确 1:空结构体作 key(零内存)
type userIDKey struct{}
ctx = context.WithValue(ctx, userIDKey{}, "123")

// ✅ 正确 2:定义命名类型(更易索引)
type ctxKey int
const (
    keyUserID ctxKey = iota
    keyTraceID
)
ctx = context.WithValue(ctx, keyUserID, "123")

包私有的自定义类型 + 包私有 / 受控的 getter / setter,能彻底杜绝跨包 key 冲突。

// 推荐模式:对外只暴露 getter/setter,key 类型保持包私有
package authctx

type userIDKey struct{}

func WithUserID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, userIDKey{}, id)
}

func UserID(ctx context.Context) (string, bool) {
    id, ok := ctx.Value(userIDKey{}).(string)
    return id, ok
}

6. 规则四:派生后立即 defer cancel()

func doWork(ctx context.Context) {
    select {
    case <-time.After(1 * time.Second):
        fmt.Println("工作完成")
    case <-ctx.Done():
        fmt.Println("工作取消:", ctx.Err())
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
    defer cancel() // ⭐ 立即 defer,哪怕 ctx 已超时

    doWork(ctx)
}

7. 规则五:不要忽略传入的 ctx,跳过用 Background()

// ❌ 错误:忽略 ctx,自起一个 Background
func handler(ctx context.Context) {
    doWork(context.Background()) // 丢失取消信号 / traceID / 超时!
}

// ✅ 正确:从传入 ctx 派生子 ctx
func handler(ctx context.Context) {
    childCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    doWork(childCtx)
}
「断链」是新人最常见错误 一旦你在中间某层用了 context.Background(),这条调用链上游的 cancel / deadline / traceID 全部丢失。下游永远等不到取消信号,可能造成 Goroutine 泄漏。

8. 规则六:不要用 WithValue 存可变对象 / 业务参数

// ❌ 不推荐:存可变对象,可能被并发修改
type Data struct{ V string }
d := &Data{V: "old"}
ctx = context.WithValue(ctx, k, d)
d.V = "new" // 跨 Goroutine 的 race 来了!

// ❌ 不推荐:把业务参数塞进 ctx
ctx = context.WithValue(ctx, "page_size", 20) // 应该作为参数

// ✅ 推荐:只存请求级元数据,且不可变
ctx = context.WithValue(ctx, traceIDKey{}, "trace-456")

10. 工程 checklist

代码 review 必查项
  • ✅ 每个长方法 / 公开方法第一个参数是 ctx context.Context
  • ✅ 调用第三方库时,优先使用接受 ctx 的版本(QueryContext、http.NewRequestWithContext)
  • ✅ WithCancel/WithTimeout/WithDeadline 之后立即 defer cancel()
  • ✅ WithValue 的 key 是包私有的自定义类型 + 配套 getter
  • ✅ 不在结构体里存 ctx
  • ✅ 不在底层函数里 context.Background() 断链
  • ✅ HTTP middleware 用 r.WithContext(ctx) 注入,handler 用 r.Context() 取

📝 练习题

  1. 写一个 HTTP middleware,从 header 取 X-Trace-ID + X-User-ID 注入 ctx,并设置 2s 整体超时。在 handler 里取出元数据并打印。
  2. 实现一个 fanout(ctx, urls),并发请求多个 URL,任意一个失败或超时则取消其它请求(用 WithCancel 派生一个公共子 ctx)。
  3. 概念题:为什么 Go 约定 ctx 总是第一个参数?为什么不能把 ctx 存进 struct?用「Service 单例 + 多并发请求」举例说明会出什么 Bug。
