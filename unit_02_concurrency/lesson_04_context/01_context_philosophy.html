4.1 Context 设计哲学

Context 用于在 Goroutine 之间传递「请求作用域」(request-scoped) 的三件事:取消信号、截止时间、元数据。 在分布式系统里,一次外部请求往往会扇出成数十个内部 RPC、数据库查询、缓存调用;只要客户端断开,或者某一层超时,所有下游工作都必须立刻停止,否则会浪费 CPU、占用连接池。Context 就是这个「广播终止」的官方机制。

Java 对照 · Context vs ThreadLocal / Future
  • Java 的 ThreadLocal 只能在单一线程中传递数据;一旦你 executor.submit() 提交到线程池,ThreadLocal 会丢失。 实际项目里要靠 MDC.getCopyOfContextMap() 手动复制,或上 TransmittableThreadLocal。
  • Java 的 Future.get(timeout) 超时只能中断当前等待,无法把信号传到下游正在执行的代码。 想真正取消,必须自己 future.cancel(true) 并依赖被中断方正确响应 InterruptedException。
  • Go 的 Context 把取消信号和请求元数据合二为一,并通过显式传参跨越所有 goroutine 边界—— 没有「忘记复制」的坑。

1. 三大设计原则

  • 不可变 (Immutable):Context 一旦创建,任何修改都不可能。每次 With* 调用都返回一个新的子 Context,而非修改原对象。 —— 这正是 Java String 不可变的同款思路,天然线程安全。
  • 链式派生 (Derive):WithCancel / WithTimeout / WithDeadline / WithValue 都接受一个父 Context,返回新的子 Context,形成一棵有向树。
  • 取消广播 (Propagate):取消一个父 Context,所有子孙 Context 会同步进入 Done 状态。下游 goroutine 只需 select { case <-ctx.Done(): } 即可感知。

2. context.Context 接口本质

type Context interface {
    Deadline() (deadline time.Time, ok bool)  // 截止时间
    Done() <-chan struct{}                    // 取消信号 channel
    Err() error                                // 取消原因
    Value(key any) any                         // 元数据查询
}

整个接口只有 4 个方法,本质上就是一个「只读通道 + 元数据 map」。 最关键的是 Done() 返回一个 channel,这意味着 Context 与 select 天然契合——你可以把 Context 和 IO/超时一起写在 select 里。

3. 超时广播的实战时序

假设你写了一个 HTTP Handler,它要并发调用 DB、Redis、外部 RPC 三个下游。Handler 给整条链路 200ms 的超时预算:

func handler(w http.ResponseWriter, r *http.Request) {
    // 派生一个 200ms 的子 Context
    ctx, cancel := context.WithTimeout(r.Context(), 200*time.Millisecond)
    defer cancel()                       // 必须 defer,否则资源泄漏

    var wg sync.WaitGroup
    wg.Add(3)
    go callDB(ctx, &wg)                  // 把 ctx 传下去
    go callRedis(ctx, &wg)
    go callRPC(ctx, &wg)
    wg.Wait()
}

关键洞察 ctx.Done() 返回的是一个 channel。当 cancel 触发,Go runtime 会 close(channel)—— 而被 close 的 channel 所有读取者都会同时收到零值,这就是 Go 实现「一对多广播」的标准技巧。

4. WithValue 的 Key 类型安全

新手最常见的错误是直接用 string 当 key:ctx.WithValue("requestID", "abc")。两个不同 package 用了同样的 "requestID" 字符串, 彼此就会意外覆盖或读到对方的数据,而且编译器不会报错。

官方做法:用自定义的私有类型当 key,这样每个 package 的 key 都是独一无二的:

// 1) 私有类型,外部 package 无法构造同样的 key
type ctxKey int

// 2) 用 const + iota 定义所有 key
const (
    keyRequestID ctxKey = iota
    keyUserID
)

// 3) 提供安全的 Set / Get 辅助函数
func WithRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, keyRequestID, id)
}
func GetRequestID(ctx context.Context) (string, bool) {
    v, ok := ctx.Value(keyRequestID).(string)
    return v, ok
}

5. 生产环境四条铁律

不要犯的四个错
  1. 不要把 Context 放进 struct。Context 是「请求作用域」对象,struct 是「实体作用域」对象。混在一起会导致 ctx 跨越生命周期边界。
  2. 不要传 nil Context。如果不确定用什么,用 context.TODO()(语义:暂时占位),不要写 nil(panic)。
  3. 不要用 WithValue 传函数参数。WithValue 只用于跨中间件传递元数据(traceID、用户身份),业务参数要走显式函数参数。
  4. 不要忘记 defer cancel()。WithTimeout / WithCancel 都会启动定时器或注册回调,不调用 cancel 会泄漏。go vet 默认会检查这一点。

6. 可运行示例

func DemoWithTimeout() {
    ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
    defer cancel()

    done := make(chan bool)
    go func() {
        time.Sleep(1 * time.Second) // 模拟慢操作
        done <- true
    }()

    select {
    case <-done:
        fmt.Println("操作完成")
    case <-ctx.Done():
        fmt.Println("⚠️ 超时:", ctx.Err()) // → context deadline exceeded
    }
}

📝 练习题

  1. 写一个三层调用链 A(ctx) → B(ctx) → C(ctx),在 A 中 WithTimeout(100ms),在 C 里 time.Sleep(200ms)。验证 C 能感知到上游超时并返回 ctx.Err()。
  2. 用 WithValue 注入一个 traceID,在每层 log 输出。再把 key 类型从 string 换成自定义 type ctxKey int,体会类型安全。
