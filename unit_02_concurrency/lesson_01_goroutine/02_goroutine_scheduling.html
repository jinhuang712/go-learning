1.2 Goroutine 调度与生命周期

2.1 G-M-P 调度模型(必看 SVG 图)

Go 调度器的核心是 G-M-P 三元组:

  • G (Goroutine) — 协程,即用户写的 go fn() 任务,持有栈和上下文。
  • M (Machine) — 操作系统线程,真正在 CPU 上跑代码。
  • P (Processor) — 逻辑处理器,持有一个本地可运行队列。M 必须绑定一个 P 才能执行 G,P 数量 = GOMAXPROCS。

(从对端偷一半) G (Goroutine) P (Processor · 数量=GOMAXPROCS) M (OS Thread) running G Global Queue
图 · G-M-P 模型: G 散布在全局队列和各 P 本地队列里, M 必须绑定 P 才能运行 G。P 空闲时会从全局或其他 P 偷一半 G(work-stealing),保证负载均衡。

2.2 Goroutine 生命周期 (6 个状态)

每个 G 都是一个状态机,在调度器中流转:

状态含义类比 Java Thread
Gidle刚分配,还未初始化NEW(但未 start)
Grunnable在某个运行队列里等待执行RUNNABLE
Grunning正在 M 上跑RUNNING
Gsyscall正在执行系统调用BLOCKED on syscall
Gwaiting等待 Channel / 锁 / GC 等条件WAITING / TIMED_WAITING
Gdead已结束,等待复用TERMINATED
stateDiagram-v2 [*] --> Gidle: newproc() Gidle --> Grunnable: 入队 Grunnable --> Grunning: 调度器挑中 Grunning --> Grunnable: time slice 用完 / Gosched() Grunning --> Gsyscall: 进入系统调用 Gsyscall --> Grunnable: syscall 返回 Grunning --> Gwaiting: chan 阻塞 / Mutex / GC park Gwaiting --> Grunnable: 被 ready() 唤醒 Grunning --> Gdead: 函数返回 / runtime.Goexit() Gdead --> [*]: 栈回收或放入 P.gFree
图 · Goroutine 状态机迁移。被阻塞的 G 不占用 M,M 可以去跑其他 G,这是 Go 调度的核心优势。

2.3 GOMAXPROCS 的作用

GOMAXPROCS 决定同时执行用户态 Go 代码的 P 数量(也就是同时跑用户代码的 OS 线程上限)。默认值等于机器逻辑 CPU 核心数。

import "runtime"

n := runtime.GOMAXPROCS(0) // 传 0 = 只读,返回当前值
runtime.GOMAXPROCS(4)      // 改成 4
Java 对照 Java 没有等价的「全局可调」CPU 数限制。最接近的是 ForkJoinPool.commonPool() 的并行度(默认 = CPU 核数 − 1),或者你自己创建的 ExecutorService.newFixedThreadPool(n)。 但 Java 这些都只是线程池大小,不影响 JVM 整体可用线程数; GOMAXPROCS 则是真正的「同时跑用户代码的 M 上限」。

线程数设置代码对照

Java:

// Java 没有直接限制线程数的机制,通常通过线程池管理
ExecutorService pool = Executors.newFixedThreadPool(4);

Go:

import "runtime"

// 控制同时执行 Go 代码的 P 数量(进而约束 M 数量)
runtime.GOMAXPROCS(4)

2.4 可运行代码示例

示例 1: GOMAXPROCS 与 Goroutine 数量监控

package main

import (
    "fmt"
    "runtime"
    "sync"
)

func main() {
    fmt.Printf("默认 GOMAXPROCS: %d\n", runtime.GOMAXPROCS(0))
    fmt.Printf("初始 Goroutine 数量: %d\n", runtime.NumGoroutine())

    runtime.GOMAXPROCS(2)
    fmt.Printf("设置后 GOMAXPROCS: %d\n", runtime.GOMAXPROCS(0))

    var wg sync.WaitGroup
    wg.Add(10)
    for i := 0; i < 10; i++ {
        go func() {
            defer wg.Done()
            for j := 0; j < 1000000; j++ {
            }
        }()
    }
    fmt.Printf("启动后 Goroutine 数量: %d\n", runtime.NumGoroutine())
    wg.Wait()
    fmt.Printf("结束后 Goroutine 数量: %d\n", runtime.NumGoroutine())
}

示例 2: runtime.Gosched() 主动让出 CPU

package main

import (
    "fmt"
    "runtime"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    wg.Add(2)

    go func() {
        defer wg.Done()
        for i := 0; i < 5; i++ {
            fmt.Println("Goroutine 1:", i)
            runtime.Gosched() // 主动让出 CPU
        }
    }()

    go func() {
        defer wg.Done()
        for i := 0; i < 5; i++ {
            fmt.Println("Goroutine 2:", i)
            runtime.Gosched()
        }
    }()

    wg.Wait()
}

2.5 调度触发时机

Go 调度是 协作式 + 抢占式混合。以下时机会触发调度:

  • 函数调用(尤其是栈扩容检查 morestack 时,会顺便检查抢占标志)
  • 系统调用前/后(entersyscall / exitsyscall hook)
  • Channel 阻塞、锁等待、GC 配合 等同步原语
  • 显式调用 runtime.Gosched()
  • 异步抢占(Go 1.14+):长时间不让出 CPU 的 G 会被信号(SIGURG)打断 — 解决了死循环卡住调度的老问题

2.6 生产环境坑点

坑点 1:盲目修改 GOMAXPROCS 默认值通常是最优的。只有在特殊场景(如容器 CPU 限制小于宿主机核数)才需要调整。 Go 1.19+ 已能自动感知 cgroup CPU 限制,但更早版本仍可能误读宿主机核数, 建议用 uber-go/automaxprocs 这类库自动对齐。
坑点 2:过度使用 runtime.Gosched() Gosched() 不保证立即被调度回来。性能关键路径上频繁调用会有反效果, 多数情况下使用 Channel 或 sync 包的同步原语更好。
坑点 3:用 Goroutine 数量衡量负载 Goroutine 数量多 ≠ 负载高,大量 Goroutine 可能只是阻塞在 IO。 应关注 CPU、内存、Goroutine 阻塞等待、p99 延迟等指标, 用 pprof 或 runtime.NumGoroutine() 只作为辅助。

📝 练习题

  1. 分别在 GOMAXPROCS=1 和 GOMAXPROCS=4 下运行多个 CPU 密集型 Goroutine,对比耗时并解释差异。
  2. 实现一个固定大小的 Worker Pool:N 个 worker Goroutine 从任务 channel 拿任务执行,主流程用 WaitGroup 等所有任务完成。
  3. 用 go tool trace 抓一次程序运行,观察 G 在 P 之间的迁移和 work-stealing 现象。
