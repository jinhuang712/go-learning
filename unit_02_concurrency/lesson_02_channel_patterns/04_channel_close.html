2.4 Channel 关闭与广播

close(ch) 把 channel 标记为「已关闭」状态,这是一个不可逆的操作。关闭后:发送会 panic,接收会立即返回,缓冲里残留的数据仍可被取出。Channel 的关闭机制是 Go 里最强大的广播原语。

1. Channel 的状态机

一个 channel 在它的生命周期里只会经过三个状态:nil → open → closed。每个状态下,send / recv / close 的行为都不一样:

stateDiagram-v2 [*] --> Nil: var ch chan T Nil --> Open: ch = make(chan T) state Open { [*] --> Empty Empty --> NonEmpty: send v NonEmpty --> Empty: recv (last) NonEmpty --> NonEmpty: send / recv Empty --> Full: send (cap=1) Full --> NonEmpty: recv } Open --> Closed: close(ch) Closed --> [*]: (GC回收) note right of Nil send: 永久阻塞 recv: 永久阻塞 close: panic end note note right of Open send: 满则阻塞,否则成功 recv: 空则阻塞,否则取数据 close: → Closed end note note right of Closed send: ❌ panic recv: 立即返回 - 缓冲有残留: 取出, ok=true - 缓冲空: 零值, ok=false close: ❌ panic (重复关闭) end note

2. 检测关闭:comma-ok 语法

v, ok := <-ch
// ok == true   : 正常收到数据
// ok == false  : channel 已关闭且缓冲为空

注意:ok == false 时 v 是零值,所以「收到 0」和「关闭」不能仅靠 v 判断。

3. for range 与关闭

for v := range ch 会持续接收,直到 channel 被 close。这是处理流式数据最自然的写法:

// 生产者
go func() {
    for i := 0; i < 5; i++ {
        ch <- i
    }
    close(ch)  // ✅ 通知接收方:没有更多数据了
}()

// 消费者
for v := range ch {
    fmt.Println(v)  // 0, 1, 2, 3, 4
}
// close 之后,for range 自然退出

4. close 当广播信号:done 模式

这是 Go 最优雅的广播原语:多个 goroutine 监听同一个 channel,关闭它就能同时唤醒所有监听者。

done := make(chan struct{})  // 0 容量, 仅作信号

// 启动 N 个 worker
for i := 0; i < 5; i++ {
    go func(id int) {
        for {
            select {
            case <-done:
                fmt.Printf("worker %d 收到停止信号\n", id)
                return
            default:
                // 干活...
                time.Sleep(50 * time.Millisecond)
            }
        }
    }(i)
}

time.Sleep(200 * time.Millisecond)
close(done)  // 🔔 所有 worker 同时收到关闭信号
time.Sleep(100 * time.Millisecond)
这才是 Go 的 broadcast Java 要广播停止信号,得用 volatile boolean + 各个线程轮询,或者 Thread.interrupt() + 处理 InterruptedException。 Go 用一个 chan struct{} + close(),就能让 N 个 goroutine 同时收到通知——这就是 context.Context 的核心机制。

5. 谁来 close?(关键设计决策)

铁律:发送方关闭,接收方不要 close
  • 关闭后发送 → panic
  • 重复关闭 → panic
  • 所以「谁发送谁关闭」最稳——发送方知道自己什么时候停

如果有多个发送方呢?这是复杂场景。两种解法:

解法 1:用一个独立的「stop」channel + sync.Once

var once sync.Once
stop := make(chan struct{})

closeStop := func() {
    once.Do(func() { close(stop) })  // 保证只 close 一次
}

解法 2:用 WaitGroup 等所有发送方完成再 close

var wg sync.WaitGroup
ch := make(chan int)

for i := 0; i < 5; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        ch <- id
    }(i)
}

go func() {
    wg.Wait()  // 等所有发送方完成
    close(ch)  // 再 close
}()

for v := range ch {
    fmt.Println(v)
}

6. Java 对照

Java 对照 Java 的 BlockingQueue 没有「关闭」概念,要表达「我不再放数据了」,常见做法是放一个 POISON_PILL 哨兵对象,消费者看到就退出——比 Go 的 close(ch) + for range 笨拙得多。

7. 4 大坑点

坑点 1:重复关闭 panic 
close(ch)
close(ch)  // ❌ panic: close of closed channel
解决:用 sync.Once,或者建立明确的 ownership 让只有一个 goroutine 负责 close。
坑点 2:关闭后发送 panic 
close(ch)
ch <- 1  // ❌ panic: send on closed channel
解决:让发送方独占关闭权;或用 select + default 配合 stop channel 检测停止信号。
坑点 3:不 close 导致 for range 死锁 
ch := make(chan int, 3)
ch <- 1; ch <- 2; ch <- 3
// 没有 close
for v := range ch { fmt.Println(v) }  // 收完 3 个后永远阻塞
坑点 4:nil channel 不能 close var ch chan int; close(ch) 直接 panic。必须先 make。

📝 练习题

  1. 用 close(done) 实现广播停止:启动 10 个 worker,主 goroutine 1 秒后停止它们,要求所有 worker 几乎同时退出。
  2. 实现安全的多生产者关闭:用 sync.Once 保证 close 只执行一次,即使多个 goroutine 同时调用。
  3. 故意触发「send on closed channel」panic,然后用 recover 捕获——理解为什么这不是好做法。
