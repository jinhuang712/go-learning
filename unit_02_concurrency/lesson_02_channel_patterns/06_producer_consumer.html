2.6 生产者-消费者模式

生产者-消费者 (Producer-Consumer) 是并发编程最经典的模式,几乎所有任务调度、消息队列、流处理都基于它。Go 用 channel + WaitGroup + 方向约束,能写出非常优雅的实现。

2. 三个核心问题

  1. 怎么分发任务? 把任务放进同一个 channel,多个 worker 用 for range 抢着读——天然负载均衡
  2. 怎么收结果? worker 把结果写回 results channel,主 goroutine 用 for range 收
  3. 怎么优雅关闭? 生产完关闭 jobs → worker 自然退出 → 等所有 worker 完成再关闭 results → 主循环退出

3. 完整可运行示例

package main

import (
    "fmt"
    "sync"
    "time"
)

func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs {           // jobs 关闭后自然退出循环
        fmt.Printf("worker %d 处理 %d\n", id, j)
        time.Sleep(100 * time.Millisecond)
        results <- j * 2            // 模拟结果
    }
}

func main() {
    jobs := make(chan int, 5)
    results := make(chan int, 5)
    var wg sync.WaitGroup

    // 启动 2 个 worker
    for i := 1; i <= 2; i++ {
        wg.Add(1)
        go worker(i, jobs, results, &wg)
    }

    // 生产者发送 5 个任务,然后关闭 jobs
    go func() {
        for j := 1; j <= 5; j++ {
            jobs <- j
        }
        close(jobs)
    }()

    // 收尾 goroutine:等所有 worker 完成再 close results
    go func() {
        wg.Wait()
        close(results)
    }()

    // 主 goroutine 收结果
    for r := range results {
        fmt.Printf("收到结果: %d\n", r)
    }
}
这段代码的精髓 worker 函数签名 jobs <-chan int, results chan<- int 用方向约束把契约写得清清楚楚——worker 只能从 jobs 读,只能往 results 写。
关闭顺序也讲究:生产者负责关闭 jobs(它知道没有更多任务) → worker 自然结束 → 收尾 goroutine 关闭 results。

4. Java 对照:相同需求的痛苦写法

Java 写法 Java 实现同样的功能: 
BlockingQueue<Integer> jobs = new ArrayBlockingQueue<>(5);
BlockingQueue<Integer> results = new ArrayBlockingQueue<>(5);
final Integer POISON_PILL = -1;                // ← 哨兵值,模拟"关闭"
ExecutorService pool = Executors.newFixedThreadPool(2);
CountDownLatch latch = new CountDownLatch(2);

for (int w = 1; w <= 2; w++) {
    pool.submit(() -> {
        try {
            while (true) {
                Integer j = jobs.take();
                if (j.equals(POISON_PILL)) {
                    jobs.put(POISON_PILL);     // ← 还得放回去给下一个 worker
                    break;
                }
                results.put(j * 2);
            }
        } catch (InterruptedException e) {}
        finally { latch.countDown(); }
    });
}
// 生产者发任务 + 1 个 POISON_PILL
// 等 latch + 关闭 results...
Java 没有 close 的概念,必须用 POISON_PILL 哨兵值,而且哨兵被消费后还要 put 回去让其他 worker 看到。代码更长、更易错。

5. 三种变体

变体 1:Worker Pool (固定 worker 数处理大量任务)

const numWorkers = 10
jobs := make(chan Job, 100)

var wg sync.WaitGroup
for i := 0; i < numWorkers; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for j := range jobs { process(j) }
    }()
}

for _, j := range allJobs { jobs <- j }
close(jobs)
wg.Wait()

变体 2:Fan-Out (一进多出,提升并行度)

// 用 N 个 worker 处理同一个上游 channel
in := source()                    // <-chan Item
for i := 0; i < numWorkers; i++ {
    go func() {
        for item := range in { process(item) }
    }()
}

变体 3:Fan-In (多进一出,合并多路结果)

func fanIn(chans ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range chans {
        wg.Add(1)
        go func(ch <-chan int) {
            defer wg.Done()
            for v := range ch { out <- v }
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

7. 生产坑点

坑点 1:多生产者,不知道谁来 close 错误做法:每个生产者发完都 close → 第二个调用 panic。
正确做法:用 WaitGroup 等所有生产者完成,在外层 goroutine 中 close。
坑点 2:results 没关闭导致主循环死锁 主 goroutine for r := range results,如果 results 永远不关,for range 就永远阻塞。
正确:用一个独立 goroutine wg.Wait(); close(results)——这就是上面例子的精髓。
坑点 3:消费者比生产者快太多 生产者跟不上,channel 长期为空,消费者频繁阻塞唤醒。调整:加大生产并行度,或减少消费 worker 数。
坑点 4:消费者比生产者慢太多 channel 容量打满,生产者被阻塞 → 整个 pipeline 卡顿。调整:加大 worker 数,或丢弃过期任务 (用 select + default)。
