2.2 无缓冲 Channel(同步通信)

无缓冲 channel 是 make(chan T) (或显式 make(chan T, 0))创建的。它的本质是一个同步点——发送和接收必须同时发生,就像两个人当面交接物品。

关键词:rendezvous (会合) 法语 "会面"。无缓冲 channel 的发送和接收必须同时到达这个会合点,先到的一方必须等后到的一方,然后直接交付数据 (零拷贝,从一个 goroutine 的栈复制到另一个)。

1. Rendezvous 会合模型

无缓冲 channel 内部没有「队列」存数据,而是维护两个等待队列:发送等待队列 sendq 和 接收等待队列 recvq。配对成功时,数据直接从发送方栈拷贝到接收方栈,不经过 channel 内部的缓冲。

图 · 无缓冲 channel 的 rendezvous (会合) 机制——两侧 goroutine 必须同时到达才能交付数据

Java 对照 Java 的 SynchronousQueue 是 ThreadPoolExecutor 默认 cached pool 用的队列——每个 execute 都需要有空闲线程立刻接走,否则就开新线程。 Go 用无缓冲 channel + 多个 worker goroutine 实现同样效果,代码量少一半。

3. 三个经典用法

用法 1:同步信号 (done 模式)

done := make(chan struct{})  // 无缓冲, struct{} 不占空间

go func() {
    fmt.Println("worker doing work...")
    time.Sleep(100 * time.Millisecond)
    done <- struct{}{}        // 发送完成信号
}()

<-done                        // 阻塞等信号
fmt.Println("worker done!")

用法 2:数据交付 (pipeline 入口)

ch := make(chan int)

go func() {
    for i := 0; i < 5; i++ {
        ch <- i * i           // 每次发送都等接收方拿走
    }
    close(ch)
}()

for v := range ch {
    fmt.Println("got:", v)
}

用法 3:确保顺序 (happens-before 保证)

// 无缓冲 channel 的 send happens-before recv,可以传递可见性
var data int

ready := make(chan struct{})
go func() {
    data = 42         // 1. 写入数据
    ready <- struct{}{} // 2. 发送 ready 信号
}()

<-ready              // 3. 接收 ready
fmt.Println(data)    // 4. 保证读到 42 (无 race)

4. 生产坑点

坑点 1:死锁 (deadlock) 
ch := make(chan int)
ch <- 42    // ❌ 同一个 goroutine 发送,没有接收方 → fatal error: deadlock
无缓冲 channel 的发送必须在另一个 goroutine 有接收方时才能成功。
坑点 2:发送和接收数量不匹配 
ch := make(chan int)
go func() { ch <- 1 }()
go func() { ch <- 2 }()  // 启动了 2 个发送
<-ch                     // 只接收 1 次
// 第二个 goroutine 永远阻塞 → goroutine 泄露
规则:发送次数 = 接收次数 + close 后丢弃的次数。
坑点 3:用无缓冲 channel 做高并发任务队列 无缓冲意味着每发一个就要等一个,吞吐量低。高并发任务建议用有缓冲 channel + worker pool。

📝 练习题

  1. 用无缓冲 channel 实现「乒乓球」:两个 goroutine 互相发送 "ping" 和 "pong" 字符串各 10 次,主 goroutine 等结束。
  2. 实现一个最简单的同步信号:启动 goroutine,主 goroutine 等待其完成 (不用 WaitGroup,只用一个 chan struct{})。
  3. 故意写一个无缓冲 channel 死锁的程序,观察 Go 输出的 fatal error: all goroutines are asleep - deadlock!
