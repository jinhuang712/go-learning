2.2 Channel 常用模式

Channel 不仅是通信工具,更是 Go 并发组合模式的基石。本节梳理 5 个最高频的: 生产者-消费者、Pipeline、Fan-out / Fan-in、信号量、Worker Pool。

2.2 模式 1: 生产者-消费者

goroutine]:::p --> CH[chan T]:::ch --> C[Consumer
goroutine]:::c classDef p fill:#a6e3a1,color:#11111b,stroke:#a6e3a1; classDef ch fill:#fab387,color:#11111b,stroke:#fab387; classDef c fill:#89b4fa,color:#11111b,stroke:#89b4fa;
图 · 经典生产者-消费者: 一对一传输,channel 起 backpressure 作用
package main

import (
    "fmt"
    "sync"
    "time"
)

func producer(ch chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    defer close(ch) // ⚠ sender 负责关闭
    for i := 0; i < 5; i++ {
        fmt.Printf("Producing: %d\n", i)
        ch <- i
        time.Sleep(100 * time.Millisecond)
    }
}

func consumer(ch <-chan int, wg *sync.WaitGroup) {
    defer wg.Done()
    for val := range ch {
        fmt.Printf("Consuming: %d\n", val)
    }
}

func main() {
    var wg sync.WaitGroup
    ch := make(chan int)

    wg.Add(2)
    go producer(ch, &wg)
    go consumer(ch, &wg)

    wg.Wait()
}
关闭契约 Channel 关闭语义遵循一个铁律: 谁发送谁关闭,且永远不要由 receiver 关闭。 receiver 不知道还会不会有 sender 来发,贸然关闭会导致其它 sender panic。

图 · Fan-in: 多个上游 channel 汇聚到一个出口,适合多源聚合(如多个 RPC 客户端的结果合并)
package main

import "fmt"

func producer(id int, ch chan<- string) {
    for i := 0; i < 3; i++ {
        ch <- fmt.Sprintf("Producer %d: message %d", id, i)
    }
}

func fanIn(ch1, ch2 <-chan string, out chan<- string) {
    for {
        select {
        case msg := <-ch1:
            out <- msg
        case msg := <-ch2:
            out <- msg
        }
    }
}

func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)
    out := make(chan string)

    go producer(1, ch1)
    go producer(2, ch2)
    go fanIn(ch1, ch2, out)

    for i := 0; i < 6; i++ {
        fmt.Println(<-out)
    }
}

2.4 模式 3: Fan-out(扇出 / Worker Pool)

flowchart LR P[Producer]:::p --> J[jobs chan]:::ch J --> W1[Worker 1]:::w J --> W2[Worker 2]:::w J --> W3[Worker 3]:::w W1 --> R[results chan]:::out W2 --> R W3 --> R R --> C[Aggregator]:::c classDef p fill:#a6e3a1,color:#11111b; classDef ch fill:#fab387,color:#11111b; classDef w fill:#cba6f7,color:#11111b; classDef out fill:#94e2d5,color:#11111b; classDef c fill:#89b4fa,color:#11111b;
图 · Fan-out / Worker Pool: 多个 worker 从同一个任务 channel 抢任务,实现并行处理
package main

import (
    "fmt"
    "sync"
)

func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for j := range jobs {
        // 模拟处理
        results <- j * 2
        fmt.Printf("worker %d done job %d\n", id, j)
    }
}

func main() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    var wg sync.WaitGroup

    // 启动 3 个 worker(Fan-out)
    for w := 1; w <= 3; w++ {
        wg.Add(1)
        go worker(w, jobs, results, &wg)
    }

    // 派发任务
    for j := 1; j <= 9; j++ {
        jobs <- j
    }
    close(jobs)

    // 关闭 results 必须等所有 worker 完成
    go func() {
        wg.Wait()
        close(results)
    }()

    for r := range results {
        fmt.Println("result:", r)
    }
}

2.5 模式 4: Pipeline 流水线

图 · Pipeline: 多个 stage 之间用 channel 连接,数据像传送带一样穿过每一阶段(类似 Java Stream 但是真并行)
// 三阶段 pipeline: gen → square → print
func gen(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            out <- n
        }
    }()
    return out
}

func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            out <- n * n
        }
    }()
    return out
}

func main() {
    for v := range square(gen(1, 2, 3, 4)) {
        fmt.Println(v) // 1 4 9 16
    }
}

2.6 模式 5: 信号量(限制并发)

Java 对照 Java 中限制并发用 java.util.concurrent.Semaphore 的 acquire() / release()。 Go 里没有内置 Semaphore 类型,但用一个带缓冲的 chan struct{} 就实现得了: 缓冲容量 = 最大并发数。 
package main

import (
    "fmt"
    "sync"
    "time"
)

func main() {
    const maxConcurrent = 3
    sem := make(chan struct{}, maxConcurrent) // 信号量
    var wg sync.WaitGroup

    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()

            sem <- struct{}{}            // 获取(满了就阻塞)
            defer func() { <-sem }()     // ⚠ 用 defer 保证释放

            fmt.Printf("Worker %d: 开始工作\n", id)
            time.Sleep(500 * time.Millisecond)
            fmt.Printf("Worker %d: 完成工作\n", id)
        }(i)
    }

    wg.Wait()
    fmt.Println("所有工作完成")
}
Java 工作池 vs Go 信号量 Java: 通常用 ExecutorService 重量级线程池管理并发。 Go: Goroutine 足够便宜,通常不需要预先建池, 用「来 1 个任务起 1 个 G + 信号量限并发」就够了 — 代码更直观,内存占用也小。

2.7 生产环境坑点

坑点 1: 忘记关闭 channel,range 永久阻塞 Producer 一定要 defer close(ch),否则下游 for range ch 永远不退出。
坑点 2: 信号量获取与释放不配对 
// 错误写法:提前 return 没释放
go func() {
    sem <- struct{}{}
    if someCondition {
        return // 漏掉 <-sem,信号量泄露!
    }
    <-sem
}()

// 正确写法:defer 兜底
go func() {
    sem <- struct{}{}
    defer func() { <-sem }()
    if someCondition {
        return
    }
}()
坑点 3: Fan-out 时无脑启动百万 G Goroutine 虽轻但不是免费 — 启动 100 万个 G 会带来 GC 压力和调度开销。 结合信号量模式或 固定 worker 数 + 任务 channel 才是工程做法。
坑点 4: 多 sender + close 配合错 多个 sender 共用一个 channel 时,谁来 close?推荐做法: 用额外的 done channel + sync.Once 或者引入一个独立的「dispatcher」goroutine 集中关闭。

📝 练习题

  1. 实现一个固定大小 Worker Pool: N 个 worker 从 jobs chan 拿任务,结果写到 results chan,主流程用 WaitGroup 等待所有完成后关闭 results。
  2. 用 pipeline 实现「生成 1..100 → 过滤偶数 → 平方 → 求和」,每一阶段用独立 goroutine。
  3. 解释 Fan-in 和 Fan-out 的区别,各举一个真实业务场景(如:聚合多个微服务结果 vs 并行抓取 N 个 URL)。
