3.3 select 坑点专项

select 强大,但也最容易踩雷。本节把生产里见过最多的几个集中讲清楚:nil channel 的隐藏行为、空 select{} 的 Goroutine 黑洞、closed channel 的零值陷阱、循环里的 timer 内存泄露。每个都给出原因 + 修复模板。

2. nil channel 在 select 中永远阻塞

这是 select 最反直觉,也是最有用的特性。一个值为 nil 的 channel,无论 send 还是 recv 操作都会永远阻塞。这意味着在 select 里,nil channel 对应的 case 永远不会被选中。

基础演示

package main

import "fmt"

func main() {
    var ch1 chan string // nil channel
    ch2 := make(chan string, 1)
    ch2 <- "hello"

    select {
    case msg1 := <-ch1: // nil channel, 永远不会被选中
        fmt.Println("收到 ch1:", msg1)
    case msg2 := <-ch2:
        fmt.Println("收到 ch2:", msg2) // 必然走这里
    }
}

应用: 动态启用/禁用 case

把变量赋成 nil,就能临时「关闭」那条 case;再赋回实际 channel 就重新启用。这在 producer 完成后想停止接收、或者 timer 触发后想关掉 ticker 等场景非常优雅。

package main

import "fmt"

func main() {
    ch3 := make(chan string, 1)
    ch3 <- "data"
    useCh3 := false

    var receiveCh3 <-chan string = ch3
    if !useCh3 {
        receiveCh3 = nil // 禁用这个 case
    }

    select {
    case <-receiveCh3: // nil → 永远不会被选中
        fmt.Println("收到 ch3")
    default:
        fmt.Println("ch3 被禁用")
    }
}
真正的生产用法 
func merge(a, b <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for a != nil || b != nil {
            select {
            case v, ok := <-a:
                if !ok { a = nil; continue }  // a 关闭后, 把它设成 nil 永远跳过
                out <- v
            case v, ok := <-b:
                if !ok { b = nil; continue }
                out <- v
            }
        }
    }()
    return out
}
合并两个 channel 时,一个先关闭就把它的局部变量赋 nil,让 select 自动忽略;两个都 nil 时 for 循环退出。完全不用 default,完全不用计数,完全不会重复读取已关闭的 channel——这是 nil channel 模式最经典的用法。

3. 空 select{} 的 Goroutine 黑洞

package main

import (
    "fmt"
    "runtime"
)

func main() {
    fmt.Println("Goroutine 数量:", runtime.NumGoroutine())

    go func() {
        select {} // 永远阻塞! Goroutine 泄露!
    }()

    fmt.Println("Goroutine 数量:", runtime.NumGoroutine())
}

空 select{} 因为没有任何 case,永远没人能让它就绪,当前 G 就被永久 park。除非你确实需要让 main G 永久挂起(比如所有工作都在子 G 里、main 只是入口),否则这是隐蔽的泄露。

合理用法 vs 滥用 合理:main() 末尾 select{} 让进程持续挂起,等待信号处理。
滥用:在子 Goroutine 里 select{} 当「假装阻塞」——这等于主动制造泄露。

4. 所有 case 都阻塞导致死锁

package main

import "fmt"

func main() {
    ch1 := make(chan int)
    ch2 := make(chan int)

    fmt.Println("等待...")
    select {
    case <-ch1: // 没有人发送
    case <-ch2: // 没有人发送
    }
    // 死锁! 整个程序无 G 可调度:
    // fatal error: all goroutines are asleep - deadlock!
}

单 G 程序里,runtime 检测到「所有 G 都阻塞」会直接 panic。多 G 程序里则不会 panic,你只能通过 pprof 看到 G 永远卡在某个 chan recv 上——更隐蔽,更难排查。

5. closed channel 的零值陷阱

ch := make(chan int)
close(ch)

// 错误: 收到零值 0, 但你可能期望「没有数据了」
val := <-ch
fmt.Println(val) // 输出 0

// 正确: 用 comma-ok
val, ok := <-ch
if !ok {
    fmt.Println("channel 已关闭")
}

在 select 里同样适用:

select {
case v, ok := <-jobs:
    if !ok {
        // jobs 已经 close 且 buffer 空, v 是零值
        // 这里通常应该退出 worker
        return
    }
    process(v)
case <-done:
    return
}

6. select 中 send 操作也会阻塞

ch := make(chan int, 1)
ch <- 1   // 缓冲满

// 错误: 缓冲区满了, send 阻塞 → 整个 select 阻塞
select {
case ch <- 2:
    fmt.Println("发送成功")
}

// 正确: 加 default 实现非阻塞 send
select {
case ch <- 2:
    fmt.Println("发送成功")
default:
    fmt.Println("发送失败, 缓冲区满")
}

7. time.After 循环内存泄露 (经典)

// 错误! 每次循环都创建一个新 Timer,
// 在 timer 触发或被 GC 之前, 它会一直被 runtime.timers 引用
for {
    select {
    case <-data:
        // 处理
    case <-time.After(5 * time.Second):
        // 超时
    }
}

// 正确: 复用 Timer
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()

for {
    select {
    case <-data:
        if !timer.Stop() {
            <-timer.C // 排掉残余信号
        }
        timer.Reset(5 * time.Second)
    case <-timer.C:
        return
    }
}
为什么 time.After 会泄露? time.After(d) 内部会创建一个 *time.Timer,并由运行时的 timer heap 持有,直到触发才会被回收。
在高频率循环里,旧 Timer 还没到点就被新 Timer 覆盖,但引用并没断——结果是 timer heap 越来越大,内存被吃光。Go 1.23+ 对此做了优化(如果 channel 上没有接收者,可以提前回收),但避开这个坑的最佳做法仍然是显式 NewTimer + Reset。

8. 综合演示: closed Channel 与 nil Channel 的差异

package main

import "fmt"

func main() {
    var nilCh chan int
    closedCh := make(chan int)
    close(closedCh)

    // 1. nil channel: 永远阻塞, default 命中
    select {
    case <-nilCh:
        fmt.Println("nil 收到")
    default:
        fmt.Println("nil → default (永远阻塞)")
    }

    // 2. closed channel: 立即返回零值
    select {
    case v, ok := <-closedCh:
        fmt.Printf("closed 收到 v=%d ok=%v\n", v, ok) // 0, false
    default:
        fmt.Println("不可能进 default")
    }
}

9. 生产环境坑点清单(速记)

坑点 1: time.After 在循环中导致内存泄露 用 time.NewTimer + Reset 取代,记得 defer timer.Stop()。
坑点 2: 忽略 closed channel 的零值 接收时永远用 v, ok := <-ch 区分「真零值」和「关闭了」。
坑点 3: select 中 send 操作的阻塞 send 也是 channel 操作,缓冲满或无接收者一样会让 select 整体阻塞。要么加 default,要么和退出/超时 case 同放。
坑点 4: 超时 case 触发后忘了 producer 端的 Goroutine 超时分支被选中后,后台 G 仍可能在往 channel send → 若 channel 无缓冲且无人接收 → producer 永久泄露。 解决:让 producer channel 容量 ≥ 1,或者在 producer 里也监听 ctx.Done()。
