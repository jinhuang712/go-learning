3.2 select 常用模式

select 单独看只是语法,真正变现是配合 time.After、default、done channel、多个数据 channel 后产生的工业级模式。这一节挑出最高频的 4 个:超时、非阻塞、多路 fan-in、退出信号。

Java 超时对照

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

public class TimeoutExample {
    public static void main(String[] args) {
        CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
            try {
                Thread.sleep(2000);
                return "任务完成";
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return "任务中断";
            }
        });

        try {
            String result = future.orTimeout(1, TimeUnit.SECONDS).get();
            System.out.println("收到结果: " + result);
        } catch (Exception e) {
            System.out.println("超时或异常: " + e.getMessage());
        }
    }
}

Go 超时对照

package main

import (
    "fmt"
    "time"
)

func main() {
    ch := make(chan string, 1)

    go func() {
        time.Sleep(2 * time.Second)
        ch <- "任务完成"
    }()

    select {
    case result := <-ch:
        fmt.Println("收到结果:", result)
    case <-time.After(1 * time.Second):
        fmt.Println("超时")
    }
}
心智迁移要点
  • Java 用 CompletableFuture 链式编程,功能强大但抽象层重;Go 把多路复用降到语法层,简单到爆。
  • Java 超时通常以异常呈现,Go 超时是一条正常的 case 分支——属于正常控制流。
  • Java anyOf / allOf 是返回新 Future 的高阶组合;Go 的 select 是「就地」组合,代码更线性。

3. 模式 1: 超时控制 (time.After)

package main

import (
    "fmt"
    "time"
)

func main() {
    resultCh := make(chan string, 1)

    // 模拟一个慢查询
    go func() {
        time.Sleep(2 * time.Second)
        resultCh <- "查询结果: 用户数据"
    }()

    // 等待结果, 但最多等 1 秒
    select {
    case result := <-resultCh:
        fmt.Println("成功:", result)
    case <-time.After(1 * time.Second):
        fmt.Println("错误: 查询超时")
    }
}
resultCh 一定要有缓冲 上面的 make(chan string, 1) 容量必须 ≥ 1。如果超时分支被选中,主 G 不会再来接收,生产者发送会永远阻塞 — 这就是经典的「Goroutine 泄露」。 容量 1 让生产者把数据塞进 buffer 后立刻返回,即使没人接收。

4. 模式 2: 非阻塞读写 (default)

package main

import "fmt"

func main() {
    ch := make(chan int, 1)

    // 非阻塞发送
    select {
    case ch <- 42:
        fmt.Println("发送成功")
    default:
        fmt.Println("发送失败 (缓冲区满)")
    }

    // 非阻塞接收
    select {
    case val := <-ch:
        fmt.Println("接收成功:", val)
    default:
        fmt.Println("接收失败 (没有数据)")
    }

    // 再次非阻塞接收 (这次没数据了)
    select {
    case val := <-ch:
        fmt.Println("接收成功:", val)
    default:
        fmt.Println("接收失败 (没有数据)")
    }
}

5. 模式 3: 多路等待 / Fan-in

package main

import (
    "fmt"
    "time"
)

func main() {
    ch1 := make(chan string)
    ch2 := make(chan string)
    stop := make(chan struct{})

    go func() {
        time.Sleep(100 * time.Millisecond)
        ch1 <- "来自服务 A"
    }()

    go func() {
        time.Sleep(200 * time.Millisecond)
        ch2 <- "来自服务 B"
    }()

    go func() {
        time.Sleep(500 * time.Millisecond)
        close(stop)
    }()

    for {
        select {
        case msg := <-ch1:
            fmt.Println("收到:", msg)
        case msg := <-ch2:
            fmt.Println("收到:", msg)
        case <-stop:
            fmt.Println("收到停止信号, 退出")
            return
        }
    }
}

6. 模式 4: 退出信号 (done channel)

close(done) 是 Go 里最优雅的「广播退出」手段——一次 close,所有监听 <-done 的 G 同时收到零值,无需逐个通知。它和 context.Done() 在底层用的是同一招。

func worker(id int, jobs <-chan int, done <-chan struct{}) {
    for {
        select {
        case j, ok := <-jobs:
            if !ok {
                return // jobs 关闭, 自然退出
            }
            fmt.Printf("worker %d 处理 job %d\n", id, j)
        case <-done:
            fmt.Printf("worker %d 收到退出信号\n", id)
            return
        }
    }
}

7. 生产环境坑点

坑点 1: 循环中 time.After 内存泄露 
// 错误: 每次循环创建新 Timer, 旧 Timer 直到触发才被 GC
for {
    select {
    case <-dataCh:
        // 处理数据
    case <-time.After(5 * time.Second):
        // 超时
    }
}

// 正确: 复用 Timer
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()

for {
    select {
    case <-dataCh:
        // 处理数据
        if !timer.Stop() {
            <-timer.C // 排掉残余信号
        }
        timer.Reset(5 * time.Second)
    case <-timer.C:
        // 超时
        return
    }
}
time.After(d) 会创建一个 *time.Timer,只有触发了才会被 GC 回收。在长时间循环里高频调用,内存会被「等待中的 Timer」吃光。
坑点 2: 非阻塞 select 写成忙等 
// 不推荐: CPU 100% 忙等
for {
    select {
    case <-ch:
        // 处理数据
    default:
        // 没有数据, 继续循环
    }
}

// 推荐: 用阻塞 select 或加短暂 sleep
for {
    select {
    case <-ch:
        // 处理数据
    default:
        time.Sleep(10 * time.Millisecond)
    }
}
非阻塞 select 在循环里跑等同于 while(true),会把一个核完全打满。如果业务允许,优先使用阻塞 select。
坑点 3: 超时精度 time.After(5 * time.Second) 不保证精确 5 秒触发——受调度延迟、GC、系统时钟分辨率影响,实际可能在 5.001s ~ 5.1s 之间。对精度敏感的场景请用 time.NewTicker 并自己累加,而不是依赖 After 的「相对秒数」。
