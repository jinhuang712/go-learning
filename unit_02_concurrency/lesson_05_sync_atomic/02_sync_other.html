5.2 sync 其他原语 · WaitGroup / Once / Cond / Map

除了 Mutex / RWMutex,sync 包还提供 4 个常用并发原语:WaitGroup(任务集等待)、Once(单次初始化)、Cond(条件变量)、Map(并发安全 map)。它们各自对应 Java java.util.concurrent 里的一个甚至多个类。

1. sync.WaitGroup · 等一组 Goroutine 全部完成

WaitGroup 内部就是一个原子计数器:Add(n) 加,Done() 减一,Wait() 阻塞直到计数归零。

var wg sync.WaitGroup

wg.Add(3)              // 计数器 +3
go func() {
    defer wg.Done()    // 计数器 -1
    // 干活
}()

wg.Wait()              // 阻塞直到计数为 0

Java 对照:CountDownLatch / CyclicBarrier / Phaser
  • CountDownLatch(n) ≈ WaitGroup,但只能用一次,Go 的 WaitGroup 在 Wait 返回后可以重新 Add 复用
  • CyclicBarrier 是循环屏障(所有线程到齐才一起放行),Go 没有内置等价物,可用 channel + atomic 自行实现
  • Phaser 是 CountDownLatch + CyclicBarrier 的进化版,功能强大但复杂

2. sync.Once · 永远只执行一次

Once.Do(f) 保证 f 在程序生命周期内有且仅有一次执行——即使被多个 Goroutine 同时调用。是懒加载单例、全局初始化的标准写法。

var (
    instance *Config
    once     sync.Once
)

func GetConfig() *Config {
    once.Do(func() {
        fmt.Println("初始化 Config(只会执行一次)")
        instance = &Config{Value: "default"}
    })
    return instance
}

Java 对照:DCL(双重检查锁) + volatile 
public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
Go 的 sync.Once 一行解决,而且默认就是正确的——Java DCL 必须配 volatile,否则在 JMM 重排序下可能拿到「半初始化」对象。

3. sync.Cond · 条件变量

当 Goroutine 需要等待某个条件满足才能继续(而不是简单的「锁释放」),用 Cond。它必须搭配一个 Mutex(或 RWMutex)使用。

var mu sync.Mutex
var cond = sync.NewCond(&mu)
var ready bool

// 消费者
go func() {
    mu.Lock()
    for !ready {        // 必须用 for!不能用 if
        cond.Wait()     // Wait 内部会先 Unlock,被唤醒后再 Lock
    }
    // 条件满足,继续干活
    mu.Unlock()
}()

// 生产者
mu.Lock()
ready = true
mu.Unlock()
cond.Signal()    // 唤醒一个等待者
// cond.Broadcast() // 唤醒所有等待者
为什么 Wait 必须在 for 循环里? 虚假唤醒(spurious wakeup):线程被唤醒后,条件可能仍然不满足(被别人抢先消费、Broadcast 唤醒了所有人但只有一个名额等)。用 for 重新检查条件,才能保证逻辑正确。这条规则在 Java Object.wait() 和 Condition.await() 上也完全一样。
实践建议:能用 channel 就别用 Cond Go 社区的强共识——条件等待 / 生产者消费者 / 信号通知,优先用 channel + select。sync.Cond 只有在「广播大量 G」或「需要细粒度控制 Wake 一个 vs 全部」的极少数场景才考虑。

4. sync.Map · 并发安全的 Map

Go 原生 map 不是并发安全的——并发写会直接 panic。sync.Map 是官方提供的并发安全替代品,适用于读多写少 / 键空间稳定场景。

var m sync.Map

m.Store("key1", "value1")
val, ok := m.Load("key1")
m.LoadOrStore("key2", "value2")     // 不存在则存,返回 (实际值, loaded)
m.Range(func(k, v any) bool {
    fmt.Printf("%v=%v\n", k, v)
    return true                      // false 中止遍历
})
m.Delete("key1")

sync.Map 不是万金油 它内部维护「只读 read map」+「可写 dirty map」双副本,写操作要同步两份。写多读少时 sync.Map 比 RWMutex+map 更慢。Go 官方文档明确建议:除非确认是「读多写少 + 键值集合稳定」,否则用 RWMutex + map[K]V。

6. 可运行示例:Once 实现单例

package main

import (
    "fmt"
    "sync"
)

type Config struct {
    Value string
}

var (
    instance *Config
    once     sync.Once
)

func GetConfig() *Config {
    once.Do(func() {
        fmt.Println("初始化 Config(只会执行一次)")
        instance = &Config{Value: "default"}
    })
    return instance
}

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            cfg := GetConfig()
            fmt.Println("Got config:", cfg.Value)
        }()
    }
    wg.Wait()
}

7. 可运行示例:sync.Map 增删改查

package main

import (
    "fmt"
    "sync"
)

func main() {
    var m sync.Map

    m.Store("key1", "value1")
    m.Store("key2", "value2")

    if val, ok := m.Load("key1"); ok {
        fmt.Println("key1:", val)
    }

    m.Range(func(key, value any) bool {
        fmt.Printf("%s: %s\n", key, value)
        return true
    })

    m.Delete("key2")
}

8. 生产环境坑点

坑点 1:WaitGroup.Add() 在 Goroutine 内部调用 
// ❌ 错误:Add() 在 G 内调用,可能 Wait() 已经返回了
go func() {
    wg.Add(1)
    defer wg.Done()
}()

// ✅ 正确:Add() 在主 G 外部、go 之前
wg.Add(1)
go func() {
    defer wg.Done()
    // ...
}()
规则:Add 必须 happens-before 对应的 Wait。错误版本里,如果调度恰好让主 G 先跑完 Wait,counter 还是 0,Wait 立即返回,后启动的 Add 反而让计数器进入诡异状态。
坑点 2:sync.Map 写多读少反而慢 sync.Map 的快路径只在「读 read map 命中」时才生效。如果你的访问模式是高频写新 key,会不断走 dirty map 的慢路径,加锁还多了一份双 map 同步开销——比 RWMutex+map 慢 2-3 倍很常见。
坑点 3:sync.Cond Wait 用 if 而非 for 
// ❌ 错误
mu.Lock()
if !ready { cond.Wait() }   // 虚假唤醒后 ready 仍可能为 false
mu.Unlock()

// ✅ 正确
mu.Lock()
for !ready { cond.Wait() }
mu.Unlock()
规则照搬 Java Object.wait():条件等待必须放在循环里。
坑点 4:Once 内 panic 后,Do 不会再执行 Once 把 Do 内的 panic 视作「已执行」——后续所有 Do 都直接返回。生产代码中 Once 内的初始化函数必须做好错误处理,否则一次失败就是永久失败。

📝 练习题

  1. 用 WaitGroup 启动 5 个 Goroutine 各打印自己的 ID,验证主 G 等所有人完成后再退出。再写一个故意把 Add(1) 放进 goroutine 内的错误版本,跑 go test -race 看会发生什么。
  2. 用 Once 实现一个并发安全的懒加载数据库连接池,然后用 100 个 Goroutine 同时 GetPool(),验证初始化函数只跑了一次。
  3. 概念题:什么时候应该用 sync.Map,什么时候应该用 RWMutex+map?给出三个判断维度。
  4. 用 sync.Cond 实现一个简易生产者消费者(队列容量 5,3 个 producer + 2 个 consumer),然后改写成基于 channel 的版本,对比哪个更易读。
