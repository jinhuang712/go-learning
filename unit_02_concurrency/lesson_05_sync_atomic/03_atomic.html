5.3 atomic · 原子操作 & 无锁编程

sync/atomic 包提供了一组「不可分割」的内存操作——加 / 读 / 写 / CAS 等都直接映射到 CPU 的原子指令(x86 上的 LOCK 前缀、ARM 上的 LDREX/STREX)。比 Mutex 快 5-10 倍,但只适合单字读写的简单场景。

1. 函数式 API vs 类型 API (Go 1.19+)

// 旧 API(仍可用):函数 + 取地址
var counter int64
atomic.AddInt64(&counter, 1)
atomic.LoadInt64(&counter)
atomic.StoreInt64(&counter, 100)
atomic.CompareAndSwapInt64(&counter, 0, 1)

// Go 1.19+ 新 API:类型化原子,更安全更易读
var counter atomic.Int64
counter.Add(1)
counter.Load()
counter.Store(100)
counter.CompareAndSwap(0, 1)
类型方法说明
atomic.Int32 / Int64Load / Store / Add / Swap / CompareAndSwap有符号整数
atomic.Uint32 / Uint64 / Uintptr同上无符号整数
atomic.Bool (Go 1.19+)Load / Store / CompareAndSwap原子布尔
atomic.Pointer[T] (Go 1.19+)Load / Store / Swap / CompareAndSwap类型安全的指针原子
atomic.ValueLoad / Store / Swap / CompareAndSwap任意类型,但每次 Store 类型必须相同

2. CAS · 乐观锁的基础

Compare-And-Swap(比较并交换)是无锁编程的核心。语义:「如果当前内存值 == old,就把它改成 new,并返回 true;否则不改并返回 false」。整个操作由 CPU 保证原子性。

// CAS 典型用法:乐观锁循环(spin loop)
for {
    old := counter.Load()
    new := old + 1
    if counter.CompareAndSwap(old, new) {
        break  // 成功
    }
    // 失败说明有人抢先改了,重新读最新值再试
}

Java 对照:AtomicInteger / VarHandle / Unsafe.compareAndSwapXxx Java 的 java.util.concurrent.atomic.* 完全等价于 Go atomic,底层都用 CPU 的 CAS 指令(x86 CMPXCHG)。Java 9+ 的 VarHandle 提供更细粒度的 memory order 控制(Plain / Opaque / Release/Acquire / Volatile),Go 的 atomic 默认就是「Sequentially Consistent」(最强顺序),不暴露弱序原语——更安全但略慢。

4. 可运行示例:原子计数器 vs 锁计数器

package main

import (
    "fmt"
    "sync"
    "sync/atomic"
    "time"
)

type AtomicCounter struct{ count int64 }

func (c *AtomicCounter) Inc()           { atomic.AddInt64(&c.count, 1) }
func (c *AtomicCounter) Get() int64     { return atomic.LoadInt64(&c.count) }

type MutexCounter struct {
    mu    sync.Mutex
    count int
}

func (c *MutexCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func main() {
    const N = 1_000_000

    ac := &AtomicCounter{}
    start := time.Now()
    var wg sync.WaitGroup
    for i := 0; i < N; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); ac.Inc() }()
    }
    wg.Wait()
    fmt.Println("Atomic:", ac.Get(), "time:", time.Since(start))

    mc := &MutexCounter{}
    start = time.Now()
    for i := 0; i < N; i++ {
        wg.Add(1)
        go func() { defer wg.Done(); mc.Inc() }()
    }
    wg.Wait()
    fmt.Println("Mutex:", mc.count, "time:", time.Since(start))
}
性能感受 在典型机器上,原子计数器通常比 Mutex 计数器快 5-10x。但高争用 + 多核时,大量 CAS 失败重试反而可能让 atomic 退化——这时候 Java 的 LongAdder(分片累加)或 Go 自己实现的「按 CPU 核分桶」就是更好的选择。

5. atomic.Value · 任意类型的原子引用

package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

type Config struct{ Value string }

func main() {
    var cfg atomic.Value
    cfg.Store(&Config{Value: "v1"})

    var wg sync.WaitGroup
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            c := cfg.Load().(*Config)
            fmt.Println("Read:", c.Value)
        }()
    }

    wg.Add(1)
    go func() {
        defer wg.Done()
        cfg.Store(&Config{Value: "v2"})
    }()

    wg.Wait()
}

典型用途:配置热更新——主 G 定期拉新配置 Store,业务 G Load 出来用,中间无需加锁。Go 1.19+ 推荐 atomic.Pointer[T](类型安全、无需断言)。

6. 生产环境坑点

坑点 1:atomic.Value 必须 Store 同一类型 
var v atomic.Value
v.Store(1)
v.Store("hello") // ❌ panic: store of inconsistently typed value
想存可变类型,要么所有 Store 都用 interface{} 包装,要么换成 Go 1.19+ 的 atomic.Pointer[T]。
坑点 2:32 位系统上 64 位原子操作必须 8 字节对齐 
// ❌ 32 位 ARM 上可能 crash
type Bad struct {
    b byte
    i int64   // 可能未对齐
}

// ✅ 把 64 位字段放在 struct 第一个,或显式 _ [...]byte 填充
type Good struct {
    i int64
    b byte
}
Go 文档对 atomic.AddInt64 等 64 位操作明确说明:在 32 位平台上,操作数必须 8 字节对齐,否则 panic。Go 1.19+ 的 atomic.Int64 类型内部会自动对齐,推荐使用。
坑点 3:用 atomic 实现复杂逻辑,可读性差 
// ❌ 复杂逻辑用 atomic 拼起来,极易写错
atomic.AddInt64(&count, 1)
if atomic.LoadInt64(&count) > 100 {  // 这里不是原子的!可能被改
    atomic.StoreInt64(&count, 0)
}

// ✅ 复杂逻辑直接用 Mutex
mu.Lock()
defer mu.Unlock()
count++
if count > 100 { count = 0 }
atomic 只保证单次操作原子,「读+判断+写」三步组合不是原子的。这种场景要么用 Mutex,要么用 CAS 循环。
坑点 4:把 atomic 当万能优化 原子操作只在真的高频争用的简单计数 / 标志位上比 Mutex 快。临界区只要稍微大一点(几行代码、调一个函数),Mutex 反而更快——因为 Mutex 失败会让 G 挂起,而 CAS 失败会一直自旋烧 CPU。
