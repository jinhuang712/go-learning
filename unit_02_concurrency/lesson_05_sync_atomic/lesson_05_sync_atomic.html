Lesson 5 · Sync 包与 Atomic 原子操作

到目前为止我们都在用 channel 实现 CSP 风格的并发——「不要通过共享内存来通信,而要通过通信来共享内存」。但实际工程中,有些场景共享内存的写法更简单 / 更快:计数器、缓存、配置热更新、单例、协调多个 worker 完成……这一课讲透 sync 包和 sync/atomic 包。

Java 对照视角 Java 的并发工具箱:synchronized + ReentrantLock + ReadWriteLock + CountDownLatch + CyclicBarrier + Condition + ConcurrentHashMap + AtomicXxx。
Go 的对应物:sync.Mutex + sync.RWMutex + sync.WaitGroup + sync.Once + sync.Cond + sync.Map + sync/atomic。
语义高度一致,但 Go 的 API 更精简,且不支持「可重入」。
学习地图 本课程围绕三个 Section 展开:先从最常用的 Mutex / RWMutex 入手,理解临界区与读写锁的权衡;然后扫一遍 WaitGroup / Once / Cond / Map 这些「场景化原语」;最后是性能至上的 atomic 包与 CAS 操作。

场景推荐原因
简单计数器、状态位atomic最快,无锁
保护一段临界区(多操作)sync.Mutex语义清晰,自带 happens-before
读多写少的缓存 / 配置sync.RWMutex多读并行
等多个 worker 全部完成sync.WaitGroupAPI 简洁
一次性初始化(单例)sync.Once取代双检锁
条件等待 / 通知sync.Cond典型生产者-消费者
键写一次后只读 / 元素互斥sync.Map无 lock 锁竞争
跨 Goroutine 数据流channelCSP 风格,语义清楚
