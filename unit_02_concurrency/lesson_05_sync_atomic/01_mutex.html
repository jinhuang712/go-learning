5.1 Mutex / RWMutex 互斥锁与读写锁

sync.Mutex 是 Go 最基础的同步原语,用来保护「临界区」(critical section):同一时间最多只允许一个 goroutine 进入。它的 API 极简——只有 Lock() 和 Unlock() 两个方法,没有 Java 那种 tryLock(timeout) / lockInterruptibly()。

能力Java ReentrantLockGo sync.Mutex

1. Mutex 基本用法

type SafeCounter struct {
    mu    sync.Mutex   // 注意:零值即可用,无需初始化
    count int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()    // 习惯性 defer,防止 panic 导致死锁
    c.count++
}

func (c *SafeCounter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}
两个语法细节
  • sync.Mutex 的零值就是「未上锁」的可用状态——不要 new(sync.Mutex),也不要 = sync.Mutex{},直接声明字段就行。
  • 把 mu 放在它保护的字段紧上方,Go 社区有这个约定俗成的命名习惯,看 stdlib 的源码就知道。

2. Mutex 状态机(Go 1.9+ 饥饿模式)

Go 的 Mutex 内部有两种模式:

  • 正常模式(默认):新到来的 goroutine 和被唤醒的 goroutine 一起抢锁。新到的因为已经在运行,有 CPU 局部性优势,通常先拿到。这种模式吞吐量最高。
  • 饥饿模式:如果一个 goroutine 等了超过 1ms 还没拿到锁,Mutex 切到饥饿模式——锁直接交给等待队列头部,新到的不再参与抢。这避免了「永远等不到」的尾延迟。

3. RWMutex 读写锁

很多业务场景读远多于写(配置缓存、路由表、用户信息),用普通 Mutex 会让所有读者排队互相阻塞。 sync.RWMutex 提供了多读单写的语义:

同时持有者读锁 RLock写锁 Lock
读锁 RLock✅ 多个并发❌ 互斥
写锁 Lock❌ 互斥❌ 互斥
 
type SafeReadWrite struct {
    mu    sync.RWMutex
    value string
}

func (s *SafeReadWrite) Read() string {
    s.mu.RLock()            // 读锁,允许多个并发
    defer s.mu.RUnlock()
    return s.value
}

func (s *SafeReadWrite) Write(v string) {
    s.mu.Lock()             // 写锁,互斥
    defer s.mu.Unlock()
    s.value = v
}

RWMutex 不是银弹
  • RWMutex 的元数据开销比 Mutex大。当临界区非常短(几十 ns 的字段读取),纯 Mutex 反而更快。
  • RWMutex 不支持升级:持有 RLock 时再调用 Lock 会死锁。需要写时,必须 RUnlock → Lock,然后重新检查状态。
  • 读 / 写比例如果不到 10:1,RWMutex 收益不明显。盲目用 RWMutex 是常见的「过度优化」。

5. 常见坑点

5.1 不可重入

// ❌ 死锁!Go 的 Mutex 不可重入
func (c *Counter) IncTwice() {
    c.mu.Lock()
    c.Inc()           // Inc 内部又 Lock → 永远等不到
    c.mu.Unlock()
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

正确做法:把临界区代码抽成一个 incLocked() 私有方法,前提是调用方已经持锁。

5.2 复制 Mutex

sync.Mutex 包含内部状态,复制后状态会脱钩。go vet 默认会报错:

// ❌ go vet: passes lock by value
func bad(m sync.Mutex) { ... }

// ✅ 永远用指针传递锁
func good(m *sync.Mutex) { ... }

// 包含 Mutex 的 struct 也要用指针接收者
func (c *Counter) Inc() { ... }   // ✅
func (c Counter)  Inc() { ... }   // ❌ go vet warning

5.3 忘记 Unlock

// ❌ 提前 return 没解锁,会永久死锁
func bad(c *Counter) error {
    c.mu.Lock()
    if err := check(); err != nil {
        return err              // 忘了 Unlock!
    }
    c.count++
    c.mu.Unlock()
    return nil
}

// ✅ 永远 defer Unlock,无视 return 路径
func good(c *Counter) error {
    c.mu.Lock()
    defer c.mu.Unlock()
    if err := check(); err != nil {
        return err
    }
    c.count++
    return nil
}

6. 何时不用 Mutex

  • 单变量读改写:用 atomic.AddInt64 / atomic.LoadInt64,无锁、最快。
  • 一次性初始化:用 sync.Once,语义比 DCL 清晰。
  • 等待一组任务完成:用 sync.WaitGroup。
  • 跨 goroutine 传递任务:用 channel,语义最 Go-style。

7. 用 -race 自我验证

把上面 SafeCounter 的 Lock/Unlock 注释掉再运行:

go test -race ./unit_02_concurrency/lesson_05_sync_atomic

race detector 会立刻打印 WARNING: DATA RACE 并指出哪两行冲突——这是验证锁是否有效的金标准。

📝 练习题

  1. 把 SafeCounter 改用 atomic.Int64 实现,对比 1M 次并发递增的延迟和 CPU。
  2. 写一个并发安全的 LRU Cache:用 RWMutex 保护 map + linked list。压测下读多写少场景与纯 Mutex 的差距。
