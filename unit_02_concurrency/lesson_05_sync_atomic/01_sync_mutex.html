5.1 sync.Mutex & RWMutex

sync.Mutex 是 Go 并发的「门卫」——保证临界区同一时刻只有一个 Goroutine 在执行。sync.RWMutex 是它的「读写分级版」,允许多个 reader 并发持锁,但 writer 独占。

1. sync.Mutex 基本用法

var mu sync.Mutex

mu.Lock()
defer mu.Unlock()
// 临界区:同一时刻只有一个 Goroutine 在这里

Mutex 内部状态机

Go 的 Mutex 不是简单的「上锁 / 释放」——为了减少调度开销,它内部有四个状态。Go 1.9 之后引入了饥饿模式(starvation mode),防止后到的 Goroutine 一直抢不到锁。

stateDiagram-v2 direction LR [*] --> Unlocked Unlocked --> Locked: Lock() · CAS 成功 Locked --> Spinning: Lock() · 其他 G 自旋抢锁
(短期 active spinning) Spinning --> Locked: CAS 抢到 Spinning --> Waiting: 自旋次数耗尽
挂入信号量等待 Locked --> Awakening: Unlock() · 唤醒一个等待者 Awakening --> Locked: 被唤醒 G 抢到锁 Awakening --> Starvation: 等待 > 1ms
转入饥饿模式 Starvation --> Locked: Unlock() 直接把锁交给队首等待者
(不让新来者抢) Starvation --> Unlocked: 队列空 / 等待者 < 1ms
退出饥饿模式 Locked --> Unlocked: Unlock() · 无等待者
图 · sync.Mutex 内部状态机 (Go 1.9+ 自带饥饿模式防止队尾饿死)
为什么需要饥饿模式? Normal 模式下,新来的 Goroutine 处于运行状态,有极强的抢锁优势——队列里的等待者(被唤醒后还要经历调度恢复)往往抢不过新来者,可能长期饥饿。Go 1.9 引入饥饿模式:如果一个等待者超过 1ms 没拿到锁,Mutex 切换到饥饿模式,Unlock 直接把锁交给队首,新来者必须排队。这保证了锁的公平性。

2. Java 对照:ReentrantLock

特性Java ReentrantLockGo sync.Mutex
可重入✅ 支持(同一线程可多次 lock)❌ 不支持(同 G 二次 Lock 直接死锁)
公平锁✅ 构造参数 new ReentrantLock(true)❌ 不支持公平模式(但有饥饿防护)
可中断✅ lockInterruptibly()❌ 不可中断(用 channel + select 模拟)
带超时✅ tryLock(timeout, unit)⚠ Go 1.18+ TryLock()(无超时)
Condition✅ 绑定在 Lock 上独立 sync.Cond,需手动传 Mutex
释放姿势try { ... } finally { unlock(); }defer mu.Unlock()
不可重入是「设计选择」,不是 Bug Go 团队明确表示:「可重入锁会让你以为自己理解了锁,但实际上你只是在掩盖糟糕的代码结构」。如果你需要在持锁状态下调一个也要持同一把锁的函数,正确做法是拆分成 lock-free 的内部函数 + 加锁的外层函数。

代码对照

// Java:ReentrantLock
import java.util.concurrent.locks.ReentrantLock;

public class Counter {
    private final ReentrantLock lock = new ReentrantLock();
    private int count = 0;

    public void increment() {
        lock.lock();
        try { count++; }
        finally { lock.unlock(); }
    }

    public int getCount() {
        lock.lock();
        try { return count; }
        finally { lock.unlock(); }
    }
}
// Go:sync.Mutex
type Counter struct {
    mu    sync.Mutex
    count int
}

func (c *Counter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func (c *Counter) GetCount() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}

3. sync.RWMutex:读写锁

多个 reader 可以同时持有读锁,但 writer 必须独占。适用于读多写少(如配置缓存、路由表)。

type Cache struct {
    rwMu sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) string {
    c.rwMu.RLock()
    defer c.rwMu.RUnlock()
    return c.data[key]
}

func (c *Cache) Set(key, value string) {
    c.rwMu.Lock()
    defer c.rwMu.Unlock()
    c.data[key] = value
}
方法语义
RLock() / RUnlock()读锁,可多个 G 同时持有
Lock() / Unlock()写锁,独占
TryLock() / TryRLock() (Go 1.18+)尝试加锁,失败立即返回 false

4. Java ReentrantReadWriteLock 对照

import java.util.concurrent.locks.ReentrantReadWriteLock;

public class Cache {
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Map<String, String> data = new HashMap<>();

    public String get(String key) {
        rwLock.readLock().lock();
        try { return data.get(key); }
        finally { rwLock.readLock().unlock(); }
    }

    public void set(String key, String value) {
        rwLock.writeLock().lock();
        try { data.put(key, value); }
        finally { rwLock.writeLock().unlock(); }
    }
}

5. 用 defer 释放锁 = 安全姿势

// ❌ 危险:忘记 Unlock,任何 panic 都会让锁永远不释放
func bad() {
    mu.Lock()
    doSomething() // 如果 panic 了,后果严重
    mu.Unlock()
}

// ✅ 标准:defer 解锁,即使 panic 也会释放
func good() {
    mu.Lock()
    defer mu.Unlock()
    doSomething()
}

6. 生产环境坑点

坑点 1:Mutex 不可重入 
var mu sync.Mutex

func foo() {
    mu.Lock()
    defer mu.Unlock()
    bar() // 💥 死锁:foo 已经持有锁
}

func bar() {
    mu.Lock() // 永远不返回
    defer mu.Unlock()
}
正确做法:把 bar 拆成「不加锁的内部 barLocked() + 加锁的外层 Bar()」。
坑点 2:复制 Mutex 
var mu sync.Mutex

// ❌ 错误:值传递会复制 Mutex,两份锁互不影响
func bad(mu sync.Mutex) {
    mu.Lock()
}

// ✅ 正确:传指针
func good(mu *sync.Mutex) {
    mu.Lock()
}

// 同理:struct 嵌入 Mutex 后,不要按值传递整个 struct
type Counter struct {
    mu    sync.Mutex
    count int
}
var c Counter
go work(c)  // ❌ 复制了 Mutex
go work(&c) // ✅ 传指针
go vet 的 copylocks 检查会捕获这类错误。
坑点 3:RWMutex 在写多读少 / 临界区极短的场景反而更慢 RWMutex 内部要维护 reader 计数,开销比 Mutex 大。判定标准:
临界区操作 < ~1μs 且写比例 > 25% → 用 Mutex 更快。
临界区操作 > ~10μs 且写比例 < 10% → RWMutex 优势明显。
坑点 4:RWMutex 不可升级 不能先持 RLock 再申请 Lock(降级亦不可),会死锁。若需要「读完再写」,直接用写锁。
坑点 5:跨 Goroutine 解锁(陷阱大坑) Go 的 Mutex不绑定 Goroutine——任何 Goroutine 都能 Unlock,即使它没有 Lock 过。这看起来很灵活,实际上是常见 Bug 源头:在 G1 里 Lock,然后 go func() { ...; mu.Unlock() }(),你永远不知道这个解锁何时发生。

📝 练习题

  1. 实现一个线程安全的计数器(Mutex 版),启动 1000 个 Goroutine 并发 Increment(),验证最终值是 1000。再写一个故意不加锁的版本,跑 go test -race 看 race detector 报警。
  2. 用 RWMutex 实现一个简单的内存缓存(Get/Set/Delete),用 benchmark 对比和 Mutex 版本在「99% 读 / 1% 写」场景下的吞吐量差异。
  3. 概念题:Go 的 Mutex 为什么不支持可重入?这是设计缺陷还是有意为之?如果业务真的需要「递归调用持锁函数」,应该怎么重构?
