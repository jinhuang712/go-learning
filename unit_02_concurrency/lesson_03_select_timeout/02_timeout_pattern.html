3.2 超时控制模式 (Timeout Pattern)

Go 没有 Java 那种 Future.get(timeout) 抛 TimeoutException 的 API。它的做法更优雅:把超时本身降级成一个 Channel,然后扔到 select 里跟业务 channel 一起赛跑,谁先到谁赢。

1. 经典超时模式

select {
case result := <-ch:
    fmt.Println("✅ 收到:", result)
case <-time.After(500 * time.Millisecond):
    fmt.Println("⚠️  超时!")
}

time.After(d) 返回一个 <-chan time.Time,运行时在 d 时长后,会往该 channel 写入一个时间值。它本身就是一个 channel。

核心心法 Go 的超时不是「中断业务 channel」,而是「赛跑」: 业务 channel 与 timer channel 同时挂在 select 上,先 ready 的赢。 没赢的一方,这次 select 不再理它(但若是 time.After,Timer 还在后台跑,见下方坑点)。

4. 完整代码示例

func DemoTimeoutPattern() {
    ch := make(chan string)

    go func() {
        time.Sleep(2 * time.Second)
        ch <- "耗时操作完成"
    }()

    select {
    case result := <-ch:
        fmt.Println("收到:", result)
    case <-time.After(500 * time.Millisecond):
        fmt.Println("⚠️  操作超时!")
    }
}

业务 sleep 2s,超时设 500ms → 输出 「操作超时!」

5. ⚠ time.After 的内存泄漏陷阱

高频生产事故 time.After 内部会 new 一个 Timer,这个 Timer 不会因为 select 走了另一个 case 而立即 GC 回收 —— 它要等到设定时间到达后才会从 runtime 的 timer 堆里释放。
在循环里用 time.After 是高频 bug 源: 
// ❌ 错误:每次循环都创建一个 Timer,业务消息频繁时积累成山
for {
    select {
    case msg := <-ch:
        process(msg)
    case <-time.After(1 * time.Hour):  // 每次循环都 new Timer!
        return
    }
}

正确写法 ① — 复用同一个 Timer:

timer := time.NewTimer(1 * time.Hour)
defer timer.Stop()
for {
    select {
    case msg := <-ch:
        process(msg)
        if !timer.Stop() {
            <-timer.C  // 排空未消费的 fire
        }
        timer.Reset(1 * time.Hour)
    case <-timer.C:
        return
    }
}

正确写法 ② — 用 context.WithTimeout(下一课 L4 详细讲):

ctx, cancel := context.WithTimeout(context.Background(), 1*time.Hour)
defer cancel()  // 一次到顶,无泄漏
for {
    select {
    case msg := <-ch:
        process(msg)
    case <-ctx.Done():
        return
    }
}
另一个常见后果 超时分支虽然返回了,但后台 goroutine 仍在运行(它不知道 caller 已经放弃)。 它如果稍后 ch <- result 到一个无缓冲 channel 并且没有别的接收者 → 这个 goroutine 永久泄漏。 生产级写法应该: ① 使用 buffered ch(留个垃圾桶接死信),或 ② 用 ctx 让业务也能感知到取消。

6. Java 对照

Java vs Go 超时
角度Java (CompletableFuture / Future)Go (select + time.After / context)
API 形态future.get(500, MS) 抛 TimeoutExceptionselect { case <-ch: case <-After: }
异常 vs 分支异常控制流 (catch)普通 case 分支
背后任务能否取消future.cancel(true) + InterruptedException必须靠 context 显式传递
资源泄漏Java Timer/Executor 自动管理需要 timer.Stop() 或 cancel()
多任务竞速CompletableFuture.anyOf(...).orTimeout(...)多 case + time.After 一锅烩
Java 把超时建模成异常路径,Go 把超时建模成一个数据路径,二者本质都是「谁先发生」,但 Go 的写法更对称、更显式。

📝 练习题

  1. 实现一个 FakeRPC(ctx context.Context, latency time.Duration): 内部 time.Sleep(latency) 后返回结果。在 main 中用 select + ctx.Done()(或 time.After) 给它套一个 100ms 超时,测试 latency=50ms / 200ms 两种情况。
  2. 把 time.After 在循环里的错误写法替换为 time.NewTimer + Reset,用 pprof 比较两者的 Timer goroutine 数量。
  3. 设计一个「重试 + 指数退避 + 总超时」工具: 总 deadline 5s 内最多重试 3 次,每次间隔 100ms / 200ms / 400ms,任何一次成功即返回。
