3.5 扇出(Fan-out)模式 · Worker Pool

Fan-out(扇出)与 Fan-in 是一对镜像: 把一个任务源 channel 的负载,分发给 N 个 worker goroutine 并行处理。这是 Go 实现 Worker Pool / 任务调度的标准姿势。

1. 拓扑图 (SVG)

图 · Fan-out 拓扑: 单一 tasks channel 被 N 个 worker 「抢着」消费,结果写回单一 results channel
关键洞察 Go channel 天然支持多消费者。N 个 worker 同时 for t := range tasks, runtime 会保证同一条任务只会被其中一个 worker 收到 —— 这就是免费的负载均衡器。

2. 完整代码示例 (3 worker, 5 task)

func worker(id int, tasks <-chan int, results chan<- int) {
    for task := range tasks {  // tasks 关闭 → range 自动退出
        fmt.Printf("Worker %d 处理任务 %d\n", id, task)
        time.Sleep(50 * time.Millisecond)
        results <- task * task
    }
}

func DemoFanOut() {
    tasks   := make(chan int, 10)
    results := make(chan int, 10)

    // 启动 3 个 worker
    for i := 1; i <= 3; i++ {
        go worker(i, tasks, results)
    }

    // 发送 5 个任务,然后 close
    for j := 1; j <= 5; j++ {
        tasks <- j
    }
    close(tasks)  // ⚠️ 必须 close,否则 worker 永远 park

    // 收集 5 个结果
    for k := 0; k < 5; k++ {
        fmt.Println("结果:", <-results)
    }
}

由于 worker 数 < 任务数, runtime 大致按 round-robin / 谁空闲谁拿 的方式分配,实际由调度器决定。

4. 通用 Worker Pool 实现

// Pool: n 个 worker 并发跑 fn,任务从 in 取,结果写 out
func Pool[T, R any](
    ctx context.Context,
    n int,
    in <-chan T,
    fn func(context.Context, T) R,
) <-chan R {
    out := make(chan R)
    var wg sync.WaitGroup
    wg.Add(n)
    for i := 0; i < n; i++ {
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case t, ok := <-in:
                    if !ok { return }
                    select {
                    case out <- fn(ctx, t):
                    case <-ctx.Done():
                        return
                    }
                }
            }
        }()
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

5. 多少个 Worker 才合适?

任务类型推荐 Worker 数原因
CPU 密集runtime.NumCPU() 或 NumCPU()-1多了只会增加调度成本,无加速
I/O 密集 (网络/DB)几十到上千都可以大部分时间 goroutine 在 park,占用 CPU 少
混合型压测找到拐点从 2*NumCPU 起步,逐倍向上试到 latency 抬头
限速 / 公平用 token bucket / 信号量额外封顶worker 数 ≠ 并发上限
关于 Goroutine 成本 一个 goroutine 初始栈只有 2KB,创建/销毁成本约 1µs 量级。比起 Java Thread(每个 ~1MB,创建成本毫秒级)便宜 1000 倍以上。 所以 Go 里开几千个 goroutine 很常见、几万也不少见,不用像 Java 那样小心翼翼维护 ExecutorService size。

6. Java 对照

Java vs Go Fan-out / Worker Pool
角度Java ExecutorService / ForkJoinPoolGo Channel + N goroutines
核心抽象线程池 + 任务队列 (Runnable / Callable)共享 channel + 多 worker goroutine
启动Executors.newFixedThreadPool(n)for i:=0; i<n; i++ { go worker(...) }
提交任务executor.submit(task)tasks <- task
结果获取Future.get() / CompletionService.take()r := <-results / range results
关闭shutdown() / shutdownNow()close(tasks) + ctx.Done()
线程/G 成本Thread ~1MB stack, 慢Goroutine 2KB,几 µs
反压队列容量 + RejectedExecutionHandler缓冲 channel 容量 + try-send default
负载均衡由 ExecutorService 实现 (work-stealing)多个 worker 共抢同一 channel,自然均衡
Java 把「池」做成一个对象,封装得很重(可监控、可配置 reject 策略); Go 用 「一对 channel + N 个 goroutine」就解决,代码量少、心智模型简单,但要自己确保关闭次序。

7. 生产环境坑点

坑点 1: 忘记 close(tasks) worker 用 for t := range tasks 阻塞读,如果生产者忘了 close(tasks),所有 worker 永远 park → goroutine 泄漏。
修复: 总有人 close,或所有 worker 都额外监听 ctx.Done()。
坑点 2: 在 worker 内部错误地 close(results) results 是 N 个 worker 共写的,任何一个 worker close 都会让其他 worker 的 results <- v panic。
正确: 用 WaitGroup.Wait() 在外部统一关 results。
坑点 3: 慢 worker 拖垮整个 pool 共享 channel 拉数据,一个 worker 卡住不会让其它 worker 拿不到任务(因为它就不读了); 但是当 worker 数 = 1 + 该 worker 死锁整池就停了。生产中要给单任务加超时/重试。
坑点 4: 结果顺序丢失 results 收到的顺序由 worker 完成快慢决定,与 task 入队顺序无关。 若需要保序,task 上带 seq id,collector 自行排序。
