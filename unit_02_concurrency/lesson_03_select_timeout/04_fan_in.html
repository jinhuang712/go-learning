3.4 扇入(Fan-in)模式 · 多路合并

Fan-in(扇入)是 CSP 中最经典的拓扑之一: 把 N 个生产者 channel 的数据,合并到一个输出 channel。下游消费者只关心「下一条数据是什么」,不关心它来自哪一路。

1. 拓扑图 (SVG)

图 · Fan-in 拓扑: N 路生产者通过 select 汇聚到单一 output channel

2. 最基础实现 (2 路 select)

func DemoFanIn() {
    ch1 := make(chan string)
    ch2 := make(chan string)
    merged := make(chan string)

    // merger goroutine: 用 select 多路接收,统一转发
    go func() {
        for {
            select {
            case msg := <-ch1:
                merged <- msg
            case msg := <-ch2:
                merged <- msg
            }
        }
    }()

    // 两路生产
    go func() { ch1 <- "A-1"; ch1 <- "A-2" }()
    go func() { ch2 <- "B-1"; ch2 <- "B-2" }()

    // 消费 4 条合并后的消息 (顺序不固定)
    for i := 0; i < 4; i++ {
        fmt.Println("合并:", <-merged)
    }
}

注意 select 多 case 同时 ready 时是伪随机(参见 3.1),所以多个 producer 不会被某一路饿死,这正是 Fan-in 天然公平的来源。

3. 通用 Merge 函数 (N 路)

当生产者数量不固定(运行期动态决定)时,不能写死 case。常见做法是「每路生产者起一个搬运 goroutine」+ sync.WaitGroup 控制 out 关闭:

// Merge: 把 N 个 <-chan T 合并成单个 <-chan T
func Merge[T any](cs ...<-chan T) <-chan T {
    out := make(chan T)
    var wg sync.WaitGroup

    output := func(c <-chan T) {
        defer wg.Done()
        for v := range c {  // 上游 close 时 range 自动退出
            out <- v
        }
    }

    wg.Add(len(cs))
    for _, c := range cs {
        go output(c)
    }

    // 所有上游都关闭后,关闭 out
    go func() {
        wg.Wait()
        close(out)
    }()

    return out
}

// 调用:
all := Merge(chA, chB, chC, chD)
for v := range all {
    process(v)
}
为什么不直接用一个大 select? Go 的 select case 数量在编译期固定。运行期 N 路时,要么用 reflect.Select(慢、丑), 要么就采用上面的「每路一个搬运 goroutine」方案。后者更地道、性能更好,也是官方 Pipelines 博客的推荐写法。

4. 何时 close 输出 channel

关键纪律
  • 只有发送方能关闭 channel(对 closed channel 再发送会 panic)。
  • Fan-in 中,merger 是 out 的发送方,所以 merger 负责 close(out)。
  • 但 merger 不能任意 close,必须等所有上游都关闭后才 close,否则下游可能漏掉消息。
  • 用 sync.WaitGroup 计数搬运 goroutine,全部 Done 后才 close(out)。

5. 进阶: Fan-in + 取消 + 第一个错误

生产级 Fan-in 通常还需要:

  • 可取消: 上游卡住时 caller 能拉闸 → 引入 ctx
  • fail-fast: 任何一路报错就整个返回 → 类似 errgroup
import "golang.org/x/sync/errgroup"

func FanInWithCtx[T any](ctx context.Context, cs ...<-chan T) <-chan T {
    out := make(chan T)
    g, ctx := errgroup.WithContext(ctx)

    for _, c := range cs {
        c := c
        g.Go(func() error {
            for {
                select {
                case <-ctx.Done():
                    return ctx.Err()
                case v, ok := <-c:
                    if !ok { return nil }   // 上游正常关闭
                    select {
                    case out <- v:
                    case <-ctx.Done():
                        return ctx.Err()
                    }
                }
            }
        })
    }
    go func() { _ = g.Wait(); close(out) }()
    return out
}

Java 派系更倾向「多生产者共写同一队列」,Go 更倾向「每个生产者一个 channel + 显式合并」。 后者表面繁琐,但类型更安全、生命周期更清晰、容易加超时/取消。

7. 生产环境坑点

坑点 1: Goroutine 泄漏 Merger 内 for { select { case v := <-ch1: ... } } 没有退出条件,主流程返回后 merger 永远 park,泄漏! 解决: 上游 close 后 case 拿到 !ok,或外层用 ctx.Done() 退出。
坑点 2: 死锁 output channel 是无缓冲的,而下游消费者已退出 → merger 写 out <- v 永久阻塞。 解决: ① 给 out 加合理缓冲;② merger 也监听 ctx.Done();③ 确保消费者退出前显式 cancel。
坑点 3: 多源数据顺序丢失 Fan-in 后顺序近似但不严格保证(取决于 select 随机选择 + Goroutine 调度)。 如果业务依赖严格顺序,需要每条消息打时间戳/序号,在下游再排序。
