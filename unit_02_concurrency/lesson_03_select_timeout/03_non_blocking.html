3.3 非阻塞 Channel 操作 (try-send / try-recv)

正常的 channel 操作是阻塞的: 收/发不成立时 goroutine 会 park。但有时我们希望「试一下,不行就走开」—— 这就是 select + default 的核心用途,等价于 Java 队列的 offer() / poll()。

1. 核心机制 · default 让 select 永不阻塞

只要 select 中带了 default 分支,Go 运行时会:

  1. 瞬时检查所有 case 是否 ready;
  2. 有就绪 → 跑 ready 的 case;
  3. 都没就绪 → 立刻跑 default,绝不挂起。
// 非阻塞发送 (try-send)
select {
case ch <- data:
    fmt.Println("✅ 发送成功")
default:
    fmt.Println("⚠️  channel 满或无接收者,丢弃")
}

// 非阻塞接收 (try-recv)
select {
case v := <-ch:
    fmt.Printf("✅ 拿到: %v\n", v)
default:
    fmt.Println("⚠️  channel 空,跳过")
}

3. 完整代码示例

func DemoNonBlocking() {
    ch := make(chan int, 1)  // 容量 = 1 的缓冲 channel

    // ① 第一次发送:成功
    select {
    case ch <- 1:
        fmt.Println("✅ 发送成功")
    default:
        fmt.Println("⚠️  channel 满")
    }

    // ② 第二次发送:失败 (buffer 已满,无人取)
    select {
    case ch <- 2:
        fmt.Println("✅ 发送成功")
    default:
        fmt.Println("⚠️  channel 满,丢弃 2")
    }

    // ③ 接收:成功
    select {
    case v := <-ch:
        fmt.Printf("✅ 拿到: %d\n", v)
    default:
        fmt.Println("⚠️  channel 空")
    }
}
// 输出:
// ✅ 发送成功
// ⚠️  channel 满,丢弃 2
// ✅ 拿到: 1

4. 典型应用场景

场景用法意图
限流 / 信号量 用 chan struct{} 当令牌桶,try-send 表示申请,拿不到则拒绝 避免压垮下游
幂等通知 ch := make(chan struct{}, 1),通知方 try-send — 哪怕 N 次也只入一条 合并冗余通知 (coalesce)
有损丢弃 (lossy queue) 生产者 try-send,满了直接丢 实时数据流(指标采样、日志降噪)
探测器 worker 周期 try-recv shutdownCh,没有就继续干活 低成本检查取消信号

4.1 合并通知示例 (coalesce notification)

// 类型: chan struct{} 用作信号 (零字节,零成本)
notifyCh := make(chan struct{}, 1)

// 生产者:多次调用都安全,最多入一个待处理信号
func notify() {
    select {
    case notifyCh <- struct{}{}:
        // 入队成功
    default:
        // 已有未处理信号在路上,合并即可,不重复
    }
}

// 消费者:处理一次代表把队列里的若干次"合并"为一次
go func() {
    for range notifyCh {
        rebuildCache()  // 合并 N 次写入为 1 次重建
    }
}()
为什么这个写法这么常用 在配置中心、热加载、缓存预热场景,「我只需要知道最近有变更,不在乎变更次数」。 用容量为 1 的 channel + try-send 就能用 3 行代码实现「合并/去重通知」。

6. 生产环境坑点

坑点 1: Busy Waiting 忙等 把 select + default 写到一个没有节流的 for 循环里,CPU 会被打到 100%: 
// ❌ 死忙等
for {
    select {
    case v := <-ch:
        process(v)
    default:
        // 啥也不做就 spin → CPU 飙满
    }
}
修复: ① 去掉 default 让它正常阻塞;或 ② default 里加 time.Sleep 节流;或 ③ 改用 for v := range ch。
坑点 2: 缓冲 channel 满 → 丢消息悄无声息 try-send 失败时,数据被「优雅丢弃」,但没有任何报错。如果业务不能容忍丢失,必须显式记录 / 打点(metrics counter) ,否则线上数据缺一截会很难定位。
坑点 3: 用 try-recv 做核心轮询 = 反模式 Channel 的设计哲学是「用阻塞代替轮询」。 如果你写了大量 for { try-recv; sleep; } 风格的代码,说明你绕开了 Go 的事件驱动, 请重构成阻塞 for-range 或 for-select。
