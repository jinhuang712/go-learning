1.3 CSP 模型核心思想

CSP 全称 Communicating Sequential Processes,由 Tony Hoare 在 1978 年提出,是 Go 并发哲学的理论基石。

Go 并发铁律 "不要通过共享内存来通信,而要通过通信来共享内存"
"Don't communicate by sharing memory; share memory by communicating."

1. CSP 的核心思想

  • 顺序进程:每个 Goroutine 内部是顺序执行的——没有「并发地写同一个变量」的烦恼
  • 同步通信:Goroutine 通过 Channel 传递消息,这也是天然的同步点
  • Channel 匿名:发送者不需要知道接收者是谁,反之亦然——彻底解耦
  • 避免显式锁:Channel 隐式提供同步,大多数场景不再需要 Mutex

2. CSP 通信流程

核心是 Producer 把数据「交」给 Channel,Channel 「转交」给 Consumer——发送和接收同时握手才完成。

sequenceDiagram participant P as Producer (goroutine A) participant C as Channel participant S as Consumer (goroutine B) Note over P,S: 场景 1:接收者先到 S->>C: <-ch (阻塞等待数据) Note over C,S: Consumer 被挂起在 channel 的 recv 队列 P->>C: ch <- v (发送 v) C->>S: 数据 v 直接交付 (零拷贝) Note over P,S: 双方同时唤醒,继续执行 Note over P,S: 场景 2:发送者先到 (无缓冲) P->>C: ch <- v (阻塞等待接收者) Note over P,C: Producer 被挂起在 channel 的 send 队列 S->>C: <-ch C->>S: 数据 v 直接交付 Note over P,S: 双方同时唤醒

4. Java 锁模型 vs Go CSP 模型

Java 风格:共享内存 + 锁 Java 并发开发者的本能是:多线程 → 共享变量 → synchronized / ReentrantLock / volatile 保护。这里数据是「共享的」,所有人都能改。 
// Java 风格:通过 synchronized 保护共享状态
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;  // 多线程同时访问需要加锁
    }
}
// Go 风格:通过 channel 通信,状态隔离在一个 goroutine 内
func counter(incrementCh <-chan struct{}, resultCh chan<- int) {
    count := 0  // 状态只属于这个 goroutine,绝不共享!
    for range incrementCh {
        count++  // 单线程访问,无锁
    }
    resultCh <- count
}

6. 反例:把 Java 风格搬到 Go

// 反 CSP 写法:Go 写出 Java 味
type BadCounter struct {
    mu    sync.Mutex
    count int
}

func (c *BadCounter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

func (c *BadCounter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}
这段代码有什么问题? 代码本身没错,但不符合 Go 的设计哲学。当状态只属于「一组操作」时,把它隔离到一个 goroutine 内,用 channel 通信,代码会更简洁、更易测试,而且天然不会有 race condition。

7. CSP 风格的等价实现

// Go 风格:通过 channel 通信
func main() {
    incCh := make(chan struct{})
    resCh := make(chan int)

    // 启动一个「持有 count」的 goroutine
    go func() {
        count := 0
        for range incCh {
            count++
        }
        resCh <- count
    }()

    // 1000 次自增请求,全部通过 channel 发起
    for i := 0; i < 1000; i++ {
        incCh <- struct{}{}
    }
    close(incCh)

    fmt.Println("Count:", <-resCh)  // 1000
}

8. 那 Mutex 还有用吗?

什么时候用 Channel,什么时候用 Mutex?
  • Channel:goroutine 之间「传递所有权」、协调流程、做 pipeline / fan-in/fan-out 模式
  • Mutex / atomic:保护真共享的状态 (如缓存 / 计数器 / 频繁读少写的配置),性能比 channel 高
Go 团队明确说过:「Don't be afraid to use mutexes if they fit your needs」。但 默认从 channel 思考,锁是退路。

9. 生产坑点

坑点 1:Java 思维惯性 Java 开发者刚入 Go 时,本能地见到「并发」就想加锁,代码到处是 sync.Mutex。 解决:每次想加锁前,先问自己「能不能把这个状态交给一个 goroutine 独占,然后用 channel 沟通?」
坑点 2:channel 死锁 fatal error: all goroutines are asleep - deadlock! 是 Go 新手最常见的运行时错误。 根因往往是:发送了数据但没有接收方,或反过来——所有 goroutine 都阻塞在 channel 上。 解决:确保每个发送都有对应的接收;用缓冲 channel 或 select + default 避免硬阻塞。
